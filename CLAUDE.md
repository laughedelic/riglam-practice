# riglam-practice: notes for Claude sessions

A practice app for Buddhist logic and debate (Dudra, Tarig). One source builds an installable PWA and a single-file Claude artifact. Read `README.md` for the layout and `docs/` for details; this file lists what a session must not get wrong.

## Commands

```sh
npm ci
npm run dev            # PWA with hot reload
npm run build          # dist/pwa and dist/artifact/index.html
npm run check:fast     # lint, typecheck, unit tests: seconds, no browser
npm run typecheck
npm run test:unit      # Vitest
npm run test:e2e       # needs both builds; PWA specs and the legacy page suite (about 5 minutes)
npm run check          # lint + typecheck + build + all tests (run before pushing)
npm run artifact:verify -- <page.html>  # is a published page the current artifact build?
npm run data:import -- <full.json>      # split a knowledge-base export into the open and the encrypted files
```

In Claude's cloud container Chromium is preinstalled and matches the pinned Playwright 1.56.1 (`/opt/pw-browsers`): do not run `playwright install`, and do not bump `@playwright/test` without the browser.

## Rules

- The page code is `src/app/app.js`, `app.css`, `markup.html`. Both builds use it. Nothing in it may depend on which build runs; `startApp(platform)` gives it its data and the `db` and `sample` capabilities (`src/platform/types.ts`), and it copes with `null`. Build differences go in `src/pwa` or `src/artifact`, which are TypeScript; new code is TypeScript.
- The live artifact (its address is kept in the Claude project, not in the repository) holds real collected answers. Republish it only from a build of this repo (`docs/ARTIFACT-LOOP.md`), keep its stored capabilities (leave `capabilities` out of the publish), and never rename a collection or change a document shape without a migration. Test builds go to a separate new artifact (`ARTIFACT_TITLE=... npm run build:artifact`).
- The term data is generated from the project's knowledge base elsewhere and kept in three files: `src/data/drill-data.json` (open: terms, relations, items) and the encrypted `course-definitions.enc` and `course-notes.enc` (`docs/DATA.md`). Never commit definitions or notes in the clear, and never write the data key (`RIGLAM_DATA_KEY`, `.data-key`) into the repo, a commit message, a PR or the project's memory. Refresh the data with `npm run data:import -- <full.json>`; do not hand-edit the files. Keep the knowledge base and these files in step. The artifact build, the parity spec and the legacy suite need the key; without it use `npm run build:pwa`.
- `src/pwa/fonts.css` and `src/pwa/fonts/` are generated by `npm run fonts`. `public/icons/` by `npm run icons`.
- `tests/legacy/` is the page's regression net, kept as it came (CommonJS scripts, mocked `window.claude`). Add new tests as Playwright specs in `tests/e2e/` or Vitest files in `tests/unit/`. A legacy test that needs another page internal gets it through the test hook block at the end of `src/app/app.js`.
- Do not widen a change beyond what was asked: the page's look was refined over many iterations (see the project notes), so layout and style changes need a reason and a before/after check at phone and desktop widths.
- Dates and statuses in the docs describe the repository, not the conversation that produced them.
- The docs in this repository are general documentation for contributors and users. Open decisions, risk or licensing analysis, the state of the owner's setup, plans and anything about who may get what stay in the Claude project's notes, not here; the repository may become public.

## Commits and pull requests

- Pull request titles are conventional commits (`feat:`, `fix:`, `chore:` ...). The repo is squash-merged and release-please reads the titles (`docs/RELEASING.md`).
- The pull request body follows `.github/pull_request_template.md` (Before / After / How).
- CI (`.github/workflows/ci.yml`) must pass: lint, build, unit, browser tests, hosting dry run, PR title.
