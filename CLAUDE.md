# riglam-practice: notes for Claude sessions

A practice app for Buddhist logic and debate (Dudra, Tarig). One source builds an installable PWA and a single-file Claude artifact. Read `README.md` for the layout and `docs/` for details; this file lists what a session must not get wrong.

## Commands

```sh
npm ci
npm run dev            # PWA with hot reload
npm run build          # dist/pwa and dist/artifact/index.html
npm run check:fast     # lint, typecheck, unit tests: seconds, no browser
npm run typecheck
npm run test:unit      # Vitest
npm run test:e2e       # needs both builds; PWA specs and the legacy page suite (about 5 minutes)
npm run check          # lint + typecheck + build + all tests (run before pushing)
npm run artifact:verify -- <page.html>  # is a published page the current artifact build?
npm run data:import -- <full.json>      # split a knowledge-base export into the open file and data-private/ (then data:publish loads the server)
```

In Claude's cloud container Chromium is preinstalled and matches the pinned Playwright 1.56.1 (`/opt/pw-browsers`): do not run `playwright install`, and do not bump `@playwright/test` without the browser.

## Rules

- The page code is in `src/app/`: `app.js` is the entry, `state.js` and the folders `core/ practice/ debate/ review/ ai/ shell/` hold the modules (`docs/ARCHITECTURE.md`), `app.css` and `markup.html` the look. Both builds use it. Shared mutable state is a property of the `state` object in `state.js`, never a module-level `let` (a unit test checks it). Nothing in it may depend on which build runs; `startApp(platform)` gives it its data and the `db` and `sample` capabilities (`src/platform/types.ts`), and it copes with `null`. Build differences go in `src/pwa` or `src/artifact`, which are TypeScript; new code is TypeScript. What the tutor is told and can look up (prompt text, the per-pair card, the lookup tools, matching a learner's words to items) is in `src/ai-shared`: pure functions of the term data that take a data index (the page passes `state`), shared with any server that calls the model. They must not touch the page, the DOM, storage or the network (a unit test checks it). The rules of the practice (which pairs there are, how the next one is drawn, how an answer is graded, how Claude's verdicts are read) are in `src/domain`, the same kind of code on top of it; change a rule there and test it in `tests/unit/domain.test.ts`, not in a page module.
- The live artifact (its address is kept in the Claude project, not in the repository) holds real collected answers. Republish it only from a build of this repo (`docs/ARTIFACT-LOOP.md`), keep its stored capabilities (leave `capabilities` out of the publish), and never rename a collection or change a document shape without a migration (the stored shapes are typed in `src/app/types.ts`). Test builds go to a separate new artifact (`ARTIFACT_TITLE=... npm run build:artifact`).
- The term data is generated from the project's knowledge base elsewhere and kept in two places: `src/data/drill-data.json` (open: terms, relations, items) is in the repository; the definitions and notes are in the git-ignored `data-private/` and in the server's database (`docs/DATA.md`). Never commit definitions or notes, and never write the Magic Key (`RIGLAM_DATA_KEY`) into the repo, a commit message, a PR or the project's memory. Refresh the data with `npm run data:import -- <full.json>` and `npm run data:publish`; do not hand-edit the files. Keep the knowledge base and these files in step. The artifact build, the parity spec, the layout specs and the legacy suite need `data-private/`; without it use `npm run build:pwa`.
- `src/pwa/fonts.css` and `src/pwa/fonts/` are generated by `npm run fonts`. `public/icons/` by `npm run icons`.
- The `staging` branch is main plus the open pull requests labeled `staging` (and the ones they are stacked on), rebuilt from scratch by the `Staging` workflow (`npm run staging -- sync`, `docs/STAGING.md`). To put a pull request on it, label it; to take it off, remove the label. Never commit to it, never open a pull request from it, never resolve a conflict on it: fix the pull request's own branch (merge `main` into it) and the workflow rebuilds. It deploys as the Worker Preview `staging` (own database and secrets), never to production.
- `tests/legacy/` is the page's regression net, kept as it came (CommonJS scripts, mocked `window.claude`). Add new tests as Playwright specs in `tests/e2e/` or Vitest files in `tests/unit/`. A legacy test that needs another page internal gets it through the test hook block at the end of `src/app/app.js`.
- Do not widen a change beyond what was asked: the page's look was refined over many iterations (see the project notes), so layout and style changes need a reason and a before/after check at phone and desktop widths.
- Dates and statuses in the docs describe the repository, not the conversation that produced them.
- The docs in this repository are general documentation for contributors and users. Open decisions, risk or licensing analysis, the state of the owner's setup, plans and anything about who may get what stay in the Claude project's notes, not here; the repository may become public.

## Commits and pull requests

- Pull request titles are conventional commits (`feat:`, `fix:`, `chore:` ...). The repo is squash-merged and release-please reads the titles (`docs/RELEASING.md`).
- The pull request body follows `.github/pull_request_template.md` (Before / After / How).
- CI (`.github/workflows/ci.yml`) must pass: lint, build, unit, browser tests, hosting dry run, PR title.
