# Architecture

## One source, two builds

The page is a plain-DOM app (no framework): the UI is built with a small `el()` helper and re-rendered as a whole, and the state is one shared object. It was written as a single artifact script and was split into the modules below without changing what it does; the browser tests are what keeps it that way.

```
src/app/  (app.js, modules, app.css + styles/, markup.html, felt-*.png)   shared by both builds
        │
        ├── src/entry-pwa.ts       + src/pwa/*    → vite build            → dist/pwa/        (PWA)
        └── src/entry-artifact.ts  + src/artifact/* → scripts/build-artifact.mjs → dist/artifact/index.html

src/platform/types.ts   the Platform interface both builds implement (and the tests mock)
src/ai-shared/          what the tutor sees and can look up: pure TypeScript over the term data, used by the page and by the Worker (worker/kit.ts)
src/domain/            the rules of the practice: pairs and their draw, grading, Claude's verdicts; pure TypeScript over the term data
```

What differs between the builds is kept out of `src/app`:

| | PWA | Artifact |
|---|---|---|
| The platform (`loadData`, `db`, `sample`, `tutor`, `reports`, `account`) | `src/pwa/platform.ts`: `db` is the local store, `sample` is `null` (in `npm run dev` a stand-in, see below), `tutor` asks the app's own server (`src/pwa/tutor.ts`), `reports` sends flags to it (`src/pwa/reports.ts`), `account` is the optional sign-in with sync (`src/pwa/account.ts`) | `src/artifact/platform.ts`: `db` and `sample` come from `window.claude`, which the artifact frame provides |
| Term data | the open data (`drill-data.json`, plain, precached); the definitions are fetched from the server with the Magic Key (from the shared link or typed) and kept on the device (`src/pwa/platform.ts`, `src/pwa/course.ts`, `src/pwa/unlock.ts`); the notes are not included | everything, merged at build time from `data-private/` (`scripts/vite-full-data.mjs`), embedded in the page's script |
| Fonts | self-hosted woff2 files (`src/pwa/fonts`, made by `npm run fonts` from the same Google Fonts link) | the Google Fonts link in `src/artifact/head.html` |
| Felt tiles | files in `dist/pwa/assets` | data URIs in the page's CSS |
| Document | `index.html` with a viewport meta, theme colour, manifest, icons | an HTML fragment (`<title>`, font links, `<style>`, markup, `<script>`); the Artifact tool adds the document skeleton |
| Ground rules of the frame | copied in `src/pwa/shell.css` (safe-area padding, `[hidden]`) | supplied by the frame |
| The first screen while the page starts | `src/pwa/cover.html` (a cover with the figure, the name and the path through the screen, drawn from the first paint with its own style and its own copy of the Hero's grain, `tests/unit/cover.test.ts` keeps both copies in step; `src/pwa/cover.ts` keeps it until the page has left its "Loading." screen and its entrance is over, then flies the figure and the name into their places at the head of the roadmap when the page opened on it, or fades it) | the frame's own |
| Service worker, install | yes | no (the frame forbids service workers) |

## The page code

```
src/app/
  app.js        the entry: startApp(platform), boot, the test hook
  state.js      the shared state: one exported object, `state`, plus the preferences saved on the device
  core/         vocabulary and helpers that depend on nothing else: relations (rel), DOM helpers (dom), viewport, small utilities
  practice/     Relations: the term universe and pair draws, grading, saving answers, favorites, skipped pairs, the screens, the terms panel
  debate/       Pervasions (the four questions): wording, flow, the screens
  find/         Find a pair (the relation is given, the learner names the pair): the draw of the relation or the one the learner picked (`rd-findrel`), the step that names the pair, the checking, the result screen; the examples and the result reuse the Relations screens
  categories/   Categories (one thing, a practice item or a reference example, the learner ticks the categories it is in, then picks the most specific): `flow.js` has the steps (tick or yes and no, check, continue, the pick), the saved answer and the offer of another stage; `screen.js` the card, the split check (what applies, what does not), the options of step 2 and the offer
  instance/     Find an instance (one to three categories, the learner names something that is all of them or says that nothing is): `flow.ts` has the draw, the answer, the check and the saved answer; it is drawn on the Path only (`path/instance.tsx`), and the classic page says so in its place
  syllogism/  Syllogisms (a subject, a predicate and a reason: deny the reason, deny the pervasion, or accept it): the draw from the answers so far, the reply, the counter-example step after "there is no pervasion" (on the Path whether the reply is right or not, so that the verdict waits for the example or for leaving it out; the classic page asks only after a right one; the subject itself is not taken: the page asks for another thing and grades nothing), the result with one sheet of its three checks, the learner's counter-example judged under the pervasion, the saved answer; the tutor's explanation and chat (`tutor.js`: the same flow as `ai/tutor.js` `ask`, which hands a syllogism to it; the card is `src/ai-shared/syllogism.ts`, there is no pair, no verdict to read back and no Quorum; the explanation is kept in `explain`); with Blitz on the reply has one countdown (`startSyllogismClock`, run by the shared clock in `debate/flow.js`), time up counts as wrong (`timeout` in the saved answer) and a right "there is no pervasion" goes straight to the result; there is no pair, so the pair bar has no star and Skip draws another
  review/       the Review screen: answers, mistakes, favorites, debate, Find a pair and Syllogisms statistics, the flags
  ai/           the tutor (asking, verdicts, chat), the examples known without it (known.js), Quorum (the chip and panel of a run, the automatic flags), flags, the one-time dialog before examples are kept (share-notice.js); the tutor's text and tools are built by src/ai-shared
  path/         the Path, the redesign behind Settings > Design (TypeScript and Preact, see below)
  shell/        rendering, the menu and the top and pair bars (menu, topbar, pbar), how panels slide in and out (motion), moving between screens (exercises, tabs), Settings (options) and the practice options of an exercise (session), the chat overlay, the system Back (history), keyboard shortcuts and timers
```

The screens: the app opens on an exercise (the one used last, `rd-ex`; Relations at first) and has no tab bar. The top bar (`shell/topbar.js`) has the menu button, the exercise's name, the Read aloud switch (a speaker, in Relations and Pervasions while Voice is on and Read aloud is chosen: it pauses and resumes the reading for this visit), the Blitz stopwatch (in Relations, Pervasions and Syllogisms, and not there when Blitz is switched off on its options page, `rd-blitzuse`; a press switches Blitz, holding it opens that page), the practice-options button and, right-most, the tutor's chat button, which waits for a result or a conversation (where no tutor can answer it is the recent answers, a clock that is drawn heavier, not filled, while its panel is open). The Blitz countdown runs along the lower edge of the top bar, over its line (`renderBar` draws `timerBar()` of `shell/timers.js` as `.mbt`): it is at the top of every exercise, where the question is, and nothing moves when Blitz is switched. On a wide screen with the right panel open it ends where the panel begins (`--coachw` in `13-layout.css`), as it begins where the pinned menu ends. The menu button keeps its place at the left, with the back arrow of Review after it. The menu (`shell/menu.js`, `EXERCISES` in `shell/exercises.js`) is today's line (it opens Review), one row per exercise, and a pinned foot with Review, Settings, a key button while this device has no Magic Key, and the version line with the way to look for an update. On a phone it is a drawer over the exercise and the root of the history; on a wide screen a panel beside the exercise, pinned until the menu button unpins it (`rd-menu`; pinned is the default, and the button is also what closes it), or that peeks from a strip at the left edge when unpinned. The menu drawer's close button sits where the menu button is (the left of its head), and the chat drawer's where the chat button is (the right). Every panel that opens (the menu, the tutor's panel, the practice options, the phone's chat) slides in from its own side, and its shade fades in on the same curve and over the same time; closing goes the same way back. The state never waits for the motion: `shell/motion.js` gives a panel that has just opened its `enter` class, and plays a closed one out from a copy of itself (`leaving`, inert and removed when over). Nothing moves under reduced motion or before the first screen is drawn. A Back that the browser animated itself (a swipe from the edge: `hasUAVisualTransition` of the popstate event) closes its panels without a second motion; a Back it did not animate (the key, the button) plays them like any other close, so the menu slides in over the exercise. The shade of a drawer or a sheet is the whole screen under it, so it fades as one thing while the panel slides. What slides in or out is cut at the inner edge of the crimson bands (`clip-path` of `.app`), so it goes under the bands and never over them. Taps show no highlight box (`-webkit-tap-highlight-color`) and a pressed control tints instead. Each exercise keeps one attempt while you are elsewhere (`shell/tabs.js`): a begun one, or one whose result is on screen, is parked and its menu row says "continue"; only Next pair moves on to a new pair. The pair bar (`shell/pbar.js`) is the foot of the exercise: Skip and the star at the left, the microphone in the middle (only while Voice is on and Answer by voice is chosen), the forward button (Next cell, Check, Next pair, with the N key hinted on a wide screen) at the right; it stays above the on-screen keyboard. A skip after part of a pair is answered asks first (`skipAsk`) and the pair waits in Review under Skipped. What changes how an exercise looks, ticks or is checked (notation, the wording of the questions, Blitz (on or off, and its times), A/B markers, full phrases, the language of the definitions, the term suggestions of Find a pair, the tutor's check and Quorum) is its practice options (`shell/session.js`): a bottom sheet on a phone and a popover on a wide screen, each option a card with its quick choice and a chevron into its own page; what only the exercise on screen has (the wording of the questions and full phrases in Pervasions, the term suggestions in Find a pair) is a section under the exercise's name, then come the options of every exercise (a new option that every exercise has goes there; Voice has its own section in Relations and Pervasions). Settings (`shell/options.js`) keeps what belongs to the app, the device and the account (Magic Key, account, your data, version and updates). A setting is in one of the two, never both. Both pause the Blitz clock. The tutor is a panel at the right on a wide screen (it opens with Explain, the automatic check or the chat button; the result stays in the middle; it closes with its pair when a tutor is there, so a new pair never starts with a panel that holds only the recent answers, and where no tutor can answer its button is the recent answers and the panel stays as long as it is wanted) and a drawer from the right over the exercise on a phone, behind a scrim, with a close button where the chat button is. The system Back closes one level at a time (the question before a skip, a page of the options, the sheet or Settings, the chat drawer, Review) and on a phone the exercise itself (the menu opens), and leaves the app only from the menu; a wide screen has no menu step, so Back leaves from the exercise. `shell/history.js` keeps one history entry per open level, each marked with its depth, and is left out in the Claude artifact's frame.

- Every variable that used to be module-level is a property of `state` (`state.ui`, `state.cur`, `state.db`, ...), because an ES module cannot assign to a binding it imports. A module-level `let` outside `state.js` fails a unit test.
- Modules import each other freely, including in cycles (the screens call the actions and the actions render). That works because only functions are called across modules, and only after loading; do not call an imported function while a module loads. Modules whose top-level code wires listeners (`core/viewport.js`, `shell/render.js`, `shell/keys.js`, `shell/history.js`, `shell/timers.js`) are imported by the entry for that effect.
- `types.ts` holds the TypeScript types of the stored documents (one per collection: answers, debates, batches, favorites, skips, flags, progress, and `labruns`, the runs of an earlier Quorum that people already hold, whose stored name stays), the pair on screen and `State`. `state.js` is annotated with `State`, so a misspelled `state.x`, or a misspelled field of a stored document, fails `npm run typecheck`. A stored shape changes there only together with a migration (see `CLAUDE.md`).
- `core/` and `state.js` import only each other, `src/ai-shared` and `src/domain` (a unit test checks it); everything else may import everything. The page imports no other code from outside `src/app`.
- What the page does around the rules (stop the clock, render, save, ask the tutor) stays in the page modules: `practice/grading.js` and `debate/flow.js` call `grade` and `gradeDebate` from `src/domain`, `practice/universe.js` calls `buildPool` and `nextPair`, and `ai/tutor.js` calls `parseVerdicts` and `applyVerdicts`; `ai/known.js` calls `referenceLines` before them for the examples the page could not check.
- `tests/unit/app-modules.test.ts` also checks that every module is reachable from `app.js`, so none is left out of a build.

## The Path

The Path is the redesign of the page, drawn by `src/app/path` into `#path` while Settings > Design says so (`rd-design`, `state.design`, kept on this device only; without a choice a Preview starts on the Path and the real app on the classic page). Its design reference is the Path Lab, a Claude artifact: the class names, the measures and the switches are the lab's.

- It is drawn with Preact (`tsconfig.json`: `jsx` with `jsxImportSource: "preact"`). The state stays where it is: the classic `render()` calls `renderPath()` (`path/index.tsx`) while the Path is on, and the Path reads `state` and calls the same actions (`choose`, `check`, `next`, `skipPair`, `setTab`, `toggleSess` ...). So Back (`shell/history.js`), the keys (`shell/keys.js`), the clocks and the stored documents work as they do on the classic page, and a screen is drawn from the same state by either design. `refreshPath()` draws the Path alone at the next frame, for what changes only it (a word typed, a note at the foot, the tutor's text as it streams).
- Which screen shows is the classic state: the roadmap is `menuOpen` (the menu), the practice options `sessOpen` and `sessPage` (the sheet has no heading of its own: while it is open the top bar names it, or its page, in place of the exercise, keeps only its close and stays live while the page behind is inert), Settings `optsOpen`, the tutor's conversation `view === "chat"`, Review `tab === "review"`, the question before a skip `skipAsk`. What only the Path has for an attempt is on `state.ui` (`pk`, `pall`, `pstrip`, `pwhy`, `pterms`, `dterm`; a case marked "nothing exists" is `cells[c].none`, as on the classic page).
- How it looks is `path/look.ts`: every switch of the lab is a setting with the owner's picks as defaults. Settings > Look takes the lab's "Copy settings" line, and keeps what differs from the defaults on the device (`rd-look`, not carried by export and import), so a later change of a default reaches every device that did not choose that setting. Colors and sizes become custom properties on `.pa`, the switches classes (`ah-dot`, `edge-fade`, `tg-nested`, ...). The tutor checks every answer by itself on the Path only where the device said so (`rd-autoexplain`), else the look's `tutorAuto`.
- The exercises are drawn on the path, one module each: `path/relations.tsx`, `pervasions.tsx`, `syllogism.tsx`, `find.tsx`, `categories.tsx` and `instance.tsx` (Find an instance, which only the Path draws), on the parts they share (`path/parts.tsx`: the pair, the choices, the verdict, the rows of the result, the tutor's Why; `path/examples.tsx`: the step of the examples, which Relations and Find a pair share). Each draws the attempt the classic flow keeps and calls its steps (`choose`, `sayQ`, `saySyllogism`, `usePair`, `tickCategory` ...), so the rules and the stored answers are the same in either design. A choice lights up for a moment before the next step comes (`pickThen`), except under a running Blitz clock.
- The next stage comes in as a station of its own on the Path (`path/stage-up.tsx`, `practice/stage-offer.ts`): when it is due (a stage that brings new terms comes with the first of them, once the stage below has brought all of its own and fewer terms are open than the learner's pace allows, whatever their marks: the stages are chapters of one list of terms, `nextStageDue` in `intro.ts`; a stage whose terms came before after a long enough run of right answers), Next on the result goes to a station that says which stage comes in ("Stage 3 reached", from the stage before, with the nine stages of course terms as a row of rings, stage 0 of everyday things not among them (`RING_STAGES` in `stages.ts`): the progression ring of each stage, `path/rings.tsx`, whose segments are the stage's new terms with the marks they have now, kept for the stages passed, with a halo on the new one; a mouse over a ring, or a tap, shows its terms in a tooltip that stays out of the page's flow) and what it introduces (Topics, with the new terms of the stage listed under it), and, under Progression, what the stages are: in full the first time, in one line with the rest folded in a later upgrade; Next from it takes the stage (the stage's first course term then comes at its stop, which the station's own Next says: "Next: new definition", `stopAfterStage` in `practice/stops.ts`). The Next station on the result before it says "Next: new stage" and is green (`stageUpDue` in `practice/stage-offer.ts`, `nextName` and `nextKind` in `path/next.ts`, `StationKind` "up"). The learner may stay on the stage they are on, and take that back with Undo (the run is then five longer, `StageRun.need`) or switch Natural progression off on the Progression page (`StageRun.manual`): then no stage comes in by itself and the learner switches them. The station is told in full once (`StageRun.told`); the run, with these three, is part of the progression document. Stage 9 is the ladder's last (`LADDER_TOP` in `stages.ts`): on the Path the stages after it are the layers of depth, which never come at a station: the result offers the next one (`DepthOffer` in `path/parts.tsx`, routed by `stageStep`), the first once the last answer on each term of stage 9 is right and the others after a run of five, and the learner sets them in the Difficulty section of the Progression page. The classic page keeps them as stages.
- The top bar (`TopBar` in `path/shell.tsx`) has a back chevron to the roadmap (the system Back does the same; there is no pull-down on the bar), the exercise's name and, after it, the progression ring (`path/progress.tsx`): on a stage with new terms it has a segment for each, in the order the learner first answered them, green while the last answer on the term is right and red after a miss (`stageMarks` and `termMark` in `intro.ts`); on one the learner stayed on or came back down to, it fills with the run of right answers towards the next stage; from stage 9 on it shows stage 9's terms, since depth is not a stage there (`stageProgress` in `stages.ts`, `progressNow` in `practice/stage-offer.ts`). It has the highest stage on in it, and a tap opens the Progression sheet, a page of the practice options sheet (`sessPage: "progress"`: the stage's name, its new terms with their marks, a line on what leads on only where a run, the learner or the last stage decides it, the nine stages' rings and the links to the Progression page; no list under it, so Back closes the sheet in one step; the bar keeps the exercise's name and the ring, shown pressed, while the other tools give way and the options button becomes the close).
- The Progression page (`path/progression.tsx`) is a page of settings lines (`path/lines.tsx`) in two sections. Difficulty gives each of the pace, the negations (with their brackets) and the depth a line and its choice (`path/difficulty.tsx`, `practice/difficulty.ts`). Stages says where the learner stands, then Natural progression (off: `StageRun.manual`), How the stages work, folded, and a line for each of the stages 0 to 9 with its ring at the right, the groups of three as headings between them (`Stage.group`); a tap unfolds a stage's new terms with their marks, and while Natural progression is off each stage has its switch on the left (the last one on stays on). Reset progression is the last line. The practice options hold neither the stages nor the difficulty. The roadmap's foot shows the rings of stages 1 to 9 alone (`StageRings`); `ProgressionAt.at` is the stage to unfold, -1 for the top of the page, `AT_STAGES` for the Stages section (a result's offer and the stage station open it there). The pace is how many course terms may be open at once before a new one waits, and how many questions apart new terms come (`PACES` and `paceSpacing` in `intro.ts`: careful two open and every four questions, steady three and three, the default, brisk five and two; the page says the chosen one in one line; `rd-pace`, the `pace` field of the progress document, which Reset progression keeps). The negations can be set from stage 2 and are suggested on a result from stage 3 (`negationSuggested` in `stages.ts`); the depth can be set from stage 9 (`withDepth`).
- Relations, Pervasions, Find a pair and Syllogisms have a guided form on the Path (`practice/guided.ts`, the rule in `stages.ts`): the relations spelled out with the pair, what Accept and Why? say, the course terms suggested while typing, what each reply of a syllogism says in S, P and R. It is on until the exercise's twentieth right answer, which turns it off once with a line on the result (`GuideNote` in `path/parts.tsx`); after that only the Guided switch in the exercise's practice options changes it. It is part of the progression (`rd-guided`, the `guided` field of the progress document), so it syncs and Reset progression turns it on again. The classic page keeps its own switches (Full phrases, Suggest terms, Show the structure).
- The other screens are drawn on the path too. Review (`path/review.tsx`) is today's trail, every answer of any exercise a stop whose color is its verdict, and the sections of the classic Review in the same grammar (the totals, the mistakes, the favorites, the pairs skipped, the flags); the numbers come from the classic review modules (`review/review.js`, `debate-stats.js`, `find-stats.js`, `syllogism-stats.js`), and a row that unfolds draws the stored answer (`path/stored.tsx`, from `storedCase` of `review/exercise.js`). Which section is open and which rows are unfolded are `state.pathSeg` and `state.pathOpen`. The tutor's conversation (`path/tutor.tsx`) is a page in the tutor's color, the newest exchange first. The flags on what the tutor wrote and Quorum's panel are `path/flags.tsx`, on the classic flag documents and steps (`ai/flags.js`). Settings and the practice options' pages (`path/settings.tsx`, `path/options.tsx`) draw their rows with the classic setters and words (`shell/options.js`, `session.js`, `levels.js`, `voice.js`); the account and your data are the shared builders of `src/ui`, given a builder that puts the Path's classes in place of the classic ones. Both are lines in groups (`path/lines.tsx`): a switch at the left where the setting can be off, the name with its value or a quick choice under it, and a chevron into its own page; the whole line is the way in. The practice options have the exercise's own lines under its name (Guided, One category at a time, Wording and notation with the wording, the notation and A and B in the text, where Off is the A/B markers), then Practice (Difficulty, today the stages' page; Blitz; Tutor explains; Voice), then "Other app settings". Settings has General (Languages, Theme), Data (Magic Key, Account with an arrow that syncs now, Share my examples, Export and import), Experiments (Design, Voice, the lab's settings; shown in a Preview, `state.preview`, or in the real app on a device with the Magic Key after a 1.5 s hold on Version, `rd-exp`) and About (Version and updates, with an arrow that checks); a line's page is `state.optsPage`, one level of the history. Blitz, the tutor and voice keep their own value in each exercise (`practice/per-exercise.ts`, `rd-per-ex`): an exercise not set yet takes the last choice made anywhere, which the shared keys keep, and the values of the exercise on screen are put in `state` as it opens.
- What the Path still hosts from the classic page (`Bridge` in `path/ui.tsx`: the nodes are built again on each draw, under `.pbr`, where the classic rules apply with the Path's colors and fonts, `39-path-bridge.css`): an exercise in a state the Path does not draw, the definition cards and the Terms panel, and the voice bar (what was heard, Confirm and Change, which `voice.js` repaints in place as it listens), above the foot, with the microphone in the Path's top bar.
- The roadmap (`path/roadmap.tsx`) lies under the exercise: the exercise and what hangs on it (the options sheet, the question before a skip, the note) are one layer (`.lay`, `app.tsx`) that slides away to the right when `menuOpen` is set (the back chevron, or the system Back) and back in from the right when it is cleared (Continue, a stop on the roadmap), the roadmap coming to its place from a little to the left under a faint shade. One motion for all of them: `.still` on the root (the browser has just animated a Back swipe itself, `hasUAVisualTransition`, or motion is off: `moves()` in `shell/motion.js`) makes the same change without the slide. There is nothing that slides from the top but the practice options. The roadmap is the root of the history at every start, also one that opens on an exercise, and Back goes to the screen the learner came from: Review and Settings opened from the roadmap stand right over it (`fromRoad`) and go back to it, by Back and by their own way back; opened from an exercise (Settings from its practice options) they go back to the exercise; only Back on the roadmap leaves the app. Chrome skips on Back the entry a page had when it added the next one before anything touched it, which a start on an exercise does, so `shell/history.js` then keeps a close watcher (`CloseWatcher`, which Android's Back asks first) that takes each Back for as long as a level is open. In the installed app the same watcher waits on the roadmap: Back there first says "Back again to close" (`leaveAsk`, for 2.5 s with no watcher), and only a second Back while it says so leaves; in a browser tab Back on the roadmap leaves at once. Continue is a link above the roadmap's foot, shown while there is an exercise to go back to. The roadmap looks for a newer version every time it opens (not while offline; `updates.check`, a look from the last few seconds stands) and shows where it stands in its version row ("Checking for updates…", "Up to date", "Update ready"); a ready version is shown in a notice above the foot, and the notice under the top bar (`pwa/update-toast.ts`) gives way while the roadmap is open (`html.road-open`). The tree has the stops and their names: Syllogisms between the two rows, Debate (planned) tied to the end of all three branches, with a dotted path fading out below it. At its head are the figure and the name "RIGLAM practice" (`path/brand.tsx`, set in Sorts Mill Goudy, the face of the Hero); the cover of the installed app flies onto them (`src/pwa/cover.ts` reads their boxes, `.rfig` and `.rbox`, and keeps the roadmap's own copies hidden with `html.cv-zoom` until it lands). A cold start opens on the roadmap (`firstScreen` in `app.js`, drawn without the slide), or on the exercise whose attempt was under way when the page was put away (`shell/keep.ts` writes a begun, unchecked attempt to `rd-attempt` on `pagehide` and when the page is hidden, and the next cold start takes it back once; coming back to a page that was not closed reloads nothing), unless `rd-start` is `"exercise"` (the browser specs set it, `tests/support/test.js`; the specs for the roadmap as the first screen set it to `"road"`); it is kept on this device only.
- The pulls (`path/gesture.ts`): the station at the foot is pulled up past a dashed line, or tapped, or taken with Enter; one that is not ready rises a little and says why. Skip is an icon under the favorites mark (`SkipMark` of `path/parts.tsx`; not on a result): with nothing written the page turns to the next one at once, with something written it asks first. The look's `skipAt: foot` puts it back as a side station at the foot instead, which slides left; a tap only nudges it, Enter takes it.
- A station says what it is by its look (`kind` of `Station` in `path/shell.tsx`, `styles/35-path-station.css`): the steps inside an exercise are medium, the size of the gray stations that wait for them (`--stp`, the label 19 px); one that leads to a question (Examples, a Pervasions question, Continue) is gold like the question steps, one that checks or shows the verdict (Check, Result) is ink, the finished. The station that goes on to the next exercise (Next pair, Next: new definition) has no kind and stays the big blue one. The copy of a station that the push rides to the new bullet (`ghostOf`) and the scanner that opens from a Check (`--s0` and `--station` of `.pscan`) start as the station is, in its size and color.
- The line (`styles/34-path-line.css`; one rule for every step): the stretch of path for a question is yellow, the path ahead is gray; a stretch is dotted while a choice or an unanswered question blocks the way on and solid once it is answered. The classes say which: `cur` yellow solid, `gap` yellow dotted (a choice, an empty field, the questions still to come), `ptail` the gray trail ahead, which follows the piece before it and, with `dtail`, stays dotted while a question of the step is unanswered even though the station is ready. In the examples each case draws its own piece from its diamond to the next (`.sx.er`, with the keyboard layout's offsets), dotted while the case is empty and solid once it has words; the trail ahead is dotted gray until every case has words, then solid gray. The same holds for the fields of Find a pair and Find an instance, the options of Categories (solid once one is ticked), the questions still to come in Pervasions and Categories, and the Syllogisms counter-example (it may stay empty and is dotted until something is written). The trail fades out downward, and the stub into the station (`.foot::before`) is gray too, dotted while the station is not ready and solid once it is, and fades upward from the station.
- Taking a choice (`path/choose.ts`, `styles/41-path-choose.css`): where `Choices` has `slide`, the marks stand beside the path and the one taken (a tap, or a finger sliding it left past half way) goes onto the line with one knock, the others fade, the dotted thread above it turns solid yellow and goes on through the mark as a solid gray one (the trail below turns solid gray with it), the mark fills, and in a list it rises to the first row's place; two short options (`row`) stand on one row. The stages are custom properties on the choice's section, played from `pickThen` before the step goes on; reduced motion, or the look's `take: lit`, lights the choice for a moment instead.
- The knocks (`bump` in `path/gesture.ts`): one short `navigator.vibrate` pulse, the hand's feedback where the screen gives none. It is made only when what touched the page last was a finger or a pen (`state.hand`, set on every `pointerdown` in `path/index.tsx`): a mouse or a trackpad has its own click, so the Path adds nothing to it, and before anything has touched the page the device's main pointer says. It knocks when a choice snaps onto the line, a station crosses its curb (and a lighter tick back under it), a side station passes its reach, the scan marks a verdict, and when a station is taken without the pull over the curb (a tap, Enter): the commitment the pull has already felt at the curb. The Vibration API has no strength to set, and the browser may hold a pulse back (silent mode, a night or battery mode, touch feedback off in the phone's settings).
- Taking a station by squeezing (`path/take.ts`, `path/gesture.ts`, `styles/42-path-take.css`, the look's `ride: fold`; the default is the push below): a station is pulled over a curb (it follows the finger, sticks at the curb until the finger has pressed on, goes over with one knock and then follows freely; pulled back it goes under again with a lighter tick), and the page folds as the station goes over (the detail under its lines goes, the lines stay) and unfolds if it goes back. Let go over the curb, or tapped, or taken with Enter, the page's lines squeeze up into its top bullet, the bullet's words go into it and it leaves through the top while the station rides up the thread and lands as the next step's first bullet; then the step goes on (`act`) and the new page comes in. The stages are custom properties on `.main`; nothing is played under reduced motion, with a running Blitz clock, for the stations that go back (`Station back`), or with the look's `ride: plain`, where the old pull (past 64 px) takes the step at once.
- Taking a station by pushing (`path/push.ts`, `styles/44-path-push.css`, the look's `ride: push`, the default; `fold` is the squeeze above): the page is strung on the thread, so the station rises into it and pushes it up as one piece (`--push` on `.pathc`, the page cut under the station's top edge by `--cut` and faded under the top bar). Held over the curb the page already follows the station (`holdPush`, a frame loop; pulled back under the curb it slides down again, `clearPush`); let go, the station keeps rising from where it is and pushes what is left out through the top (`playPush`), coming to rest where the next step's first bullet will be, as the big diamond, then the step goes on: the station itself goes with the step, so a copy of it (`ghostOf`) rests at the new bullet, waits a beat and turns into it (smaller, the bullet's color) while the page comes in; the look's `land: recoil` has it go a little past the bullet and come back. A page that keeps its statement across the step (`data-keep` on the last element of it, after its `.stm` lines, its value the px the result leaves above the statement; a syllogism's S, P and R before its Result) is not pushed: its heading fades and its room folds (`foldBefore`) so that the statement is already where the result puts it, what follows it folds into it, the station comes to its foot and the result opens there, the verdict's node coming out of the station; the line along the statement goes from the question's gold to the walked ink as the station starts to rise (the section's `--sc`, registered with `@property` in `34-path-line.css` so that it can be eased). A station that stands on the page itself rides as the squeeze does. What is at the foot while a station rides away from it is a placeholder for the station that comes next (`path/foot.ts`, `styles/45-path-foot.css`; the push and the Check's scan have it, the squeeze does not): the gray empty diamond of a station that is not ready (`Hold`: a copy of the station, `.fw-sd`), with the foot's stub of thread whole again, gray and fading, above it (`.fw-ph` on the main), is born when the station goes over the curb, or as it rises when taken by a tap, or as the Check's scanner leaves; it is let go if the station is pulled back. Nothing joins it to the station that rides away, and the foot shows no real station (`wait` puts `.fw-wait` on the main) until the step has landed and the page's thread runs down to the foot again; then `activate` takes the placeholder away and `come` brings in the real station of the new page as what it is (`.fw-act`: its diamond from the placeholder's look to its own color, its mark and its words after it: Next pair, or a question's gray Check).
- The Check of the examples (`path/examples.tsx`): once the last example has words, the Check is the next stop and the line runs solid to the foot. With the keyboard up there is no foot and no station on the page: Enter on the last example opens the page first (`openThen` in `path/relayout.ts`: the keyboard goes, the parts move to the page's layout and the foot comes in with the Check), and the Check is taken from the foot once it stands still, as on a screen with no keyboard. While the page opens the layout of the keyboard is held (`Pull.hold`, `Pull.after` in `app.tsx`), so it changes once, under the animation.
- The Check of Categories' first step (`path/categories.tsx`) slides up the same way (`scanPlan`: the rows over the rule, then the rest, marked where they stand; it stops under the thing, `.cstop`, which keeps the thing and folds the heading away), and the result keeps the threshold as the learner left it, each category marked (`Settled`). Its rows are matched to the page checked by their key (`data-k` there, `data-mk` in the result), so they stay where they were.
- Taking the Check of the examples (`path/scan.tsx`, `styles/43-path-scan.css`; the look's `check: morph` is the default, `scan` the swap below): the Check does not ride. Its diamond opens into a hollow scanner that slides up the thread in one move, and each case is marked as the scanner passes it (its diamond takes the verdict's color, its mark comes after the example); the heading's words go as it is covered; at the strip's edge the relation is marked (struck or checked, with a knock); the scanner settles into the heading's place, fills with the verdict's color and shows the result's word; then the check is taken and the result's page comes in, the scanner gliding the short way into its node. The verdicts are graded before the check by `scanPlan` (`path/relations.tsx`, with `grade` of `src/domain/grading.ts`, as the check grades them); the page's own nodes are only given classes and marks. With the keyboard up (the folded layout) the page opens first (`path/relayout.ts` moves each part from where it was to where it is now) while the scanner glides to the foot, and the scan runs over the opened page; at the foot, a placeholder for the station that comes next takes the Check's place as the scanner leaves it, and the real one comes in once the scanner is the result's node (`path/foot.ts`). The result's page is drawn and starts to come in within one frame (`drawn`: a draw that waits for the next frame is followed by a callback registered after it), so it is never seen whole before it fades in. The default, `check: morph`, does not swap the pages when the scan is over (`check: scan` does): the case rows (by their names), the parts of the pair (its figure, the two terms, the relation given with its mark, taken from the strip) move from where they stood to where the result has them (`translate` and `scale` animations from the old rectangles; the strip's leftovers, a clone of it, fade where they are), the result's node and word are held back from the moment the page is swapped until the scanner has glided in, and the rows the result has more of, its classes and the relation it should have been come in after the moved ones. A syllogism's Result takes the same scan (`ScanPlan.stop`, `scanPlan` in `path/syllogism.tsx`): there is no strip, so the scanner rises through the counter-example, if one is written (its case is marked), stops at the reply's row, marks the reply (checked, or struck when it is not the right one) and flashes its verdict, and becomes the result's node there; the heading above the statement folds (`foldBefore` of `path/push.ts`) as it rises, so the statement is where the result has it when the page is swapped, and does not come in again. Nothing is scanned when the check will not go on (the subject itself is no counter-example). Pervasions' relation, which checks as it is picked, takes the same scan from its gray Result station (`Pull.scanPick`, `pickThen`'s `scan`): once the picked relation has slid onto the path the scanner, gray as the station it leaves, rises from the foot, marks the relation and then the four answered questions (`ScanPlan.rows`, graded by `gradeDebate` before the check), and becomes the result's node at the first heading (`ScanPlan.stop`); the choice stays as it was taken until the page is swapped. The look's `check: ride` takes it as any station; reduced motion, a running clock and `ride: plain` take it at once.
- The Path is one column on every screen for now (`isWide()` is false while it is on), and the installed app carries its fonts (Newsreader, Kalam, IBM Plex Mono, and Spectral and Pangolin for the letters those lack).

## The tutor code

`src/ai-shared/` is TypeScript with no dependency on the page. It holds everything that decides what the tutor sees and can look up:

| File | What |
|---|---|
| `data.ts` | the types of the term data (`DrillData`, `Term`, `Cat`, `Item`) |
| `lookup.ts` | `norm`, `makeIndex(data)` (the lookup tables), `matchItem`, `catByLabel`, `categoryOf` (the practice category a learner's words name, by label or by Dudra term), `pairCats`: how a learner's words resolve to a practice item or category; `upChain` (a term and its parents) and `classNames` (the classes of the "is a" tree the tutor names an example's class from) |
| `mentions.ts` | `termMentions(index, text)`: the Dudra terms a text names, by name, alias or plural, the longest first; names that are everyday words (one, reason, definition, cause) and words in quotation marks do not count. `termNamed(index, text)` is the term a whole text stands for (a name given as one of the two phenomena of a pair). The tutor's notes and the Terms panel underline these terms and open their definitions in place (`withTerms` in `src/app/practice/terms.js`) |
| `relations.ts`, `debate.ts` | the five relations, the four cells and the four questions in their canonical wording; a negated side: `NEG_CELL` (where a thing goes), `negLabel` ("non-(wooden things)") and `plainLabel` |
| `facts.ts` | `termFacts`, `catFacts`: what the data says about a term or category |
| `prompts.ts` | the tutor's standing instructions and the "explain" requests: for Relations, Pervasions, and Find a pair (one for a pair the page can judge, one, `FIND_ASK_OWN`, for a pair it cannot, where the tutor also says which relation the pair has) |
| `card.ts` | `tutorCard(index, pair, answer)`: the first message of a tutor chat, made of the instructions, `cardBody(index, pair, answer)` (the data, the relation, the learner's answer and the page's verdicts) and `cardNotes(index, pair)` (the fine points from the sources, from `finePoints(index, categoryIds)`); a server that holds the instructions and the fine points itself asks for the body only; `explainAsk(answer)` |
| `examples.ts` | the types of the reference examples ([DATA.md](DATA.md)), `readExamples` (a tolerant reader), `makeExampleIndex` and `matchExamples` (every example a learner's words name), `exampleFacts` (what the tutor is told about one), `examplesFor(index, items, term, max, level)` (the examples of a term: its own first, then the plainest, a spread of subclasses; the definition card and the tutor's `examples_of` use it) |

| `tools.ts` | `tutorTools(index, examples?)`: the `lookup_term` and `classify_example` tools; given the reference examples, `classify_example` falls back to them and a third tool, `examples_of`, lists the examples of a term up to a level |

Every function takes a **data index** (`DataIndex`: the data plus its lookup tables) as its first argument. The page passes its `state`, which has the same five fields (`DATA`, `CAT`, `ITEMIDX`, `ALIASIDX`, `LABELIDX`); `indexData()` in `practice/universe.js` fills them with `makeIndex`. Code that talks to the model elsewhere builds an index with `makeIndex(data)` and gets the same prompt text and the same tool results. `tests/unit/ai-shared.test.ts` checks the functions on made-up data and the real open data, and that the folder imports nothing outside itself and touches no `window`, `document`, storage or network.

The page's JavaScript imports these files with their `.ts` extension; Vite compiles them for both builds.

The pair keeps its categories in `catA` and `catB` and says which side is negated in `neg`; its cells are the plain pair's moved by `NEG_CELL`, so the relation, the examples and the reason for an empty cell (the plain pair's reason) come from the same data. No relation says anything about the neither cell, and only a pair with a negated side can have it empty: a plain pair always has the horn of a rabbit there, which is in no category, while a negation takes in what does not exist. The learner says so in that cell ("nothing exists"), and only in that cell: the other cases are written whenever the relation chosen asks for them. Such a pair is still four possibilities when each of the other three cells has something (Perdue 2014 names it four possibilities without neither, after Kensur Yeshi Thupten; Perdue 1992, after Lati Rinpoche, three possibilities without there being something which is neither). `judgeText` places a listed example by the negated cells, and the tutor's facts on a negated side are read in reverse (`placeFacts`); the tutor's card names the negation and sets aside, for that pair, the general rule that only Neither takes what does not exist (`negLine`; `explainAsk` says it too), and the server's review of a flag gets the pair with its negation. What the server learned of examples is said of the categories themselves, so a negated pair neither asks for it nor sends its examples to be kept. A negated pair is a favorite of its own (`favKey` names the negated side with `non_`). A preview once offered the case as a sixth relation, `4n`; an answer, favorite, skip or flag saved with it is read as four possibilities (`fromSixth`). A pair with A alone negated (`neg: "a"`) is not known to a version of the page from before it, so it is for devices that have taken the update. In Pervasions, Q4 asks for something that is neither: accepting it says that nothing is neither, which a pair with a negation can have, and the relation stays what Q1 to Q3 give (`deriveRel`). Find a pair takes a negation as the learner names it ("non-wooden things"; either side, `neg: "a"` or `"b"`; with the Brackets switch as it is, `nameThing` and `findPair` take it), with the Negations choice off too. The track is offered on a result of Relations (`practice/negations.ts`, after the offer of another stage, which goes first when both are due): after five right relations in a row on plain pairs, one side; after five on negated pairs, both sides; nothing changes without the tap, and an offer passed over or declined waits for another run (`rd-neg-offer`, part of the progression). On the Path the offer comes from stage 3, and only while fewer terms are open than the learner's pace allows.

Randomness is a parameter (`rng`, `Math.random` by default), so the same data and the same random numbers give the same pairs. `tests/unit/domain.test.ts` checks the rules on made-up data and, on the real open data, that the right answer is graded ok for every pair the page can draw; it also checks that the folder imports nothing but itself and `src/ai-shared` and touches no `window`, `document`, storage or network.

## The platform

The page does not depend on which build runs it (Settings only shows which build it is, through `about()` below). Each entry file calls `startApp(platform)` (the export of `app.js`), and the platform (`src/platform/types.ts`) offers three things:

- `loadData()`: the term data. When it rejects, the page shows its "no data" screen.
- `db()`: the document store, or `null`. Without it the page runs, but saves nothing.
- `sample()`: model calls, or `null`. The Claude artifact's own capability: the page picks the models itself and gives the model its tools.
  In `npm run dev` the PWA has a stand-in (`src/pwa/dev-sample.ts`): it calls no model and answers with fixed text in the shape the page reads (the lines of an explanation, a verdict for each example the page could not check), streamed word by word, so these parts can be built and their layout tried without a key or a server. `?ai=off` in the address takes it away, `?ai=slow` streams slowly, `?ai=rate_limited` and `?ai=error` make it fail as the page's error messages expect. The stand-in is imported behind `import.meta.env.DEV`, so no build contains it; `tests/unit/pwa-build.test.ts` checks `dist/pwa`.
- `about()` (optional): which build runs (version, commit, build time) and whether the server has a newer one, for the Version row in Settings and the version line of the menu. The PWA knows its own commit from the build (`vite.config.js`) and compares it with `build.json` next to the page, which the service worker does not precache; a staging build also lists its branches from `staging-build.json`. The artifact has none.
- `updates` (optional property): updating the installed app in place (`src/pwa/updates.ts`). A new service worker takes over as soon as it is installed (`skipWaiting`): one that waits for every page of the app to close never gets its turn on a phone, where closing the app often leaves a page alive and a cold start opens the old version again. The page that is open keeps running the version it loaded, so the app looks for a newer one when it starts, when it returns to the screen after 15 minutes, when the connection returns and when Settings opens; the page is never reloaded without the reader's word (they may be in the middle of an answer), so a version that takes over is offered in a toast under the top bar (`src/pwa/update-toast.ts`; it goes away on "Later" or by itself) and in the Version row of Settings and the version line of the menu, and "Update now" reloads onto it. `index.html` also holds a small inline script: if the page still says "Loading." after 12 seconds it offers a reload and a reload that drops the service worker and its cached files (stored answers and settings are not touched). The artifact has no `updates`.
- `tutor()` (optional): a question to the app's own server ([SERVER.md](SERVER.md)), or `null`. The request is the conversation and the pair's categories; the server holds the instructions, the lookup tools and the notes. The PWA offers it when this device has the Magic Key and the server's `/api/health` says its tutor is on. The page uses `sample` when it has one, else `tutor`; with neither it hides the tutor and Explain.
- `reports()` (optional): sends a learner's flag, with the stored answer it was made on, to the app's server ([SERVER.md](SERVER.md), "Flag reports"), or `null`: the place has no server for flags, or this device lacks the Magic Key. It has `send`, `status`, `withdraw` and `flush`, none of which rejects. The page (`src/app/ai/flag-reports.js`) marks a sent flag with `sentAt`, and keeps the server's reply and the state of its review on the flag as `review` (asked at the start and when Review is opened, at most once a minute). It talks to the server about flags one request at a time, in the order it made them, so that an older upload cannot arrive after a newer one or after the flag's removal. A flag removed while `reports()` gave `null` (offline at the start) is kept by `withdrawReport` and taken back at a later start that has the capability. The artifact build has none, and a device without the key cannot flag.
- `quorum()` (optional): what the app's server offers of Quorum, the tutor's mode of several models and a judge: `"on"` (on until the device turns it off), `"optin"` (off until the device turns it on) or `false`; absent in the artifact. The PWA answers from `/api/health` when this device has the Magic Key; only a Preview offers it today ([SERVER.md](SERVER.md), "Quorum"). It is a mode of `tutor`: with the practice-options switch on, an explain question carries `quorum: true` and the answer comes with the run for the chip. The page keeps the device's own choice (`rd-quorum`), which wins over the server's default.
- `examples()` (optional): the reference examples a device with the Magic Key keeps ([DATA.md](DATA.md)), or `null`. They arrive in the background after the page started, so a later call may have them where the first had none: `onExamples(tell)` says when a newer copy was kept. The page reads them into `state.EX` (`src/app/core/examples.js`: at the start, after a key was taken in place, and when `onExamples` fires); what shows examples reads `state.EX` when it draws. The artifact build embeds the device part when `data-private/` has it (`virtual:riglam-examples`); without it, or in the PWA without the key, the page has none.
- `known()` (optional): what the app's server learned of examples from earlier checks ([SERVER.md](SERVER.md), "Learned facts"), or `null`. The PWA offers it when this device has the Magic Key and `/api/health` says `known: "on"`. After a check the page asks it about the examples still open, waiting a few seconds at most, before the tutor is asked; it never rejects. The artifact build has none.
- `shares()` (optional): whether the app's server keeps what the tutor's answers say of the learner's examples ([SERVER.md](SERVER.md), "Learned facts"). The PWA says yes when this device has the Magic Key and `/api/health` says `learns: "on"`. The page then asks the learner once, before the first explain question that would name examples goes out (`ai/share-notice.js`: a native modal dialog that has to be answered; `ask()` in `ai/tutor.js` waits for it), and offers the switch "Share my examples" in Settings (`rd-share`; `rd-share-told` is the device's memory of having been told); with the switch off an explain question names no examples. The artifact build has none.
- `account()` (optional): the optional account, or `null`: a passkey to sign in with and a server copy of the documents ([SERVER.md](SERVER.md), "Accounts and sync"). It has a view (who is signed in, what is waiting to be sent, the last message), `subscribe`, and the actions `signUp`, `signIn`, `addPasskey`, `signOut`, `deleteAccount` and `syncNow`. The PWA offers it when `/api/health` says accounts are on, or when this device used one before; Settings then shows an Account row. The artifact build has none.

The shapes of `db` and `sample` are the artifact runtime's (`collection/doc/where/orderBy/limit/onSnapshot`; one call from a prompt or turns), so the artifact adapter passes `window.claude` through and the PWA implements the same interface locally. The page does not branch on the build. The PWA entry also leaves the platform at `window.__riglam.platform` for the browser tests and the console.

A block at the end of `src/app/app.js` is the test hook (`window.__riglamTest`, inert unless a test defines it).

## The local `db`

`src/pwa/local-db.ts` implements the part of the artifact runtime's `db` that the page uses and a bit more (documents at `collection/id`, `get/set/update/delete`, `where/orderBy/limit/get/onSnapshot`, `add`, `acquire`; frozen snapshots; `invalid_argument` and `TypeError` rules from the runtime's `db.d.ts`). Reads come from memory, writes go to IndexedDB (database `riglam`, store `docs`), other tabs are told through a `BroadcastChannel`. If IndexedDB is not available (some private modes) the app keeps working in memory for that session.

When a server arrives, a second adapter with this interface replaces it; the page does not change.

## Account and sync (the device side)

`src/account/` is the part that does not depend on the page or the browser, so the Worker's tests can run it against the real server code: `protocol.ts` (the contract shared with the Worker), `client.ts` (one function per route, failures as codes), `sync.ts` (the engine), `outbox.ts` and `idb-outbox.ts` (what is waiting to be sent), `account.ts` (the view and the actions the Settings row uses), `passkeys.ts` and `webauthn.ts` (the browser's passkeys, with the options and results converted to and from JSON by hand). `src/pwa/account.ts` joins them to the local store, Web Locks (one tab syncs at a time) and the events that mean "try now": the connection returning, the page becoming visible, a minute passing. `src/ui/account.ts` is the Settings row.

The local store tells sync about each write the page makes (`LocalDb.onWrite`) and takes the server's copies without telling it back (`LocalDb.applyRemote`). Each change is noted in the outbox, one entry per document, in its own IndexedDB database (`riglam-sync`), with the time it was made. A round sends the entries and receives what changed on the server. A copy from the server replaces the local one unless the local document was changed after that copy was made; then the local change is sent next. A write the page has begun but not yet noted (`LocalDb.writing`) counts as a change too: the copy waits for the next round, and the cursor does not move past it (the copies already applied are recognized again). A copy the store refuses because of a newer write (`applyRemote` says whether it stored it) is put off the same way. Notes of one document that finish out of order do not undo each other's retry. A sync that was asked for (sign-out, Sync now) waits for the lock another tab holds, where a background round leaves the work to that tab. Changes of account run one after the other, each only if its person is still the one shown, and the end of a round (its failure included) is dropped when the account changed meanwhile. The server's copy is stored in the same IndexedDB transaction that checks the row still holds what this tab has in memory, so a newer write by another tab, not yet heard of, is not overwritten. A change of account waits for the writes still being saved and for their notes before it clears the queue, so a late write is noted for the account it was made under; a sign-out that comes while a change of account waits wins, and the change does not turn sync on afterwards. Signing out asks the server whose session it is about to end, and does not end it when another tab has signed in as someone else. When the server says accounts are off, a remembered person is forgotten and sync stops. Changes are noted from the first sign-in on, also while signed out, so nothing made offline or between sessions is lost. The first sign-in on a device offers every document it already has, at the timestamp the document carries. A different person signing in on the same device starts over the same way. A scan that failed or was cut short is started again by the next round. An answer that arrives after the account changed (here or in another tab) is dropped without being applied, and its requests are sent again. A request the server calls too large for the account's daily allowance is sent again with half as many changes. A write that the server did not take (its copy is newer) stays in the outbox until the server's copy has been stored here, so a failed store is answered again. When the server says the account holds as many documents as it may (`full`, which does not end at midnight), the deletions go first, what other devices changed is still received, and the Account row says so. The outbox keeps an index on the change time (IndexedDB version 2, added when an older database is opened), so a batch is read without loading the queue. A failed round is tried again after 15 seconds, doubling up to 15 minutes; a refusal for the day's limit waits an hour.

## Export and import

Settings has a "Your data" row. Export writes everything the page keeps (the documents of the collections below and the `rd-*` settings in localStorage) to one JSON file, `riglam-practice-data` version 1; on a phone it opens the share sheet, elsewhere it downloads. Import reads such a file, shows what it would add and replace, and writes only after the person confirms. It never deletes: a document that is already there is replaced only by a copy with a later timestamp (`at`, `verifiedAt` or `updatedAt`), settings already set on the device are kept, and importing a file twice changes nothing. The comparison is made again for each document just before it is written, because the preview can be old (a flag change or another tab may have saved a newer copy meanwhile); such documents are left alone and counted. Documents called `__proto__` are left out, since the page builds objects keyed by document id. The logic is `src/store/transfer.ts` (it works on any `Db`, so it serves the artifact too and a later server adapter), the row is `src/ui/data-transfer.ts`. A change to a stored shape needs a migration of old files in `parseDataFile`, which is why the file carries a version.

Collections the page uses: `batches`, `answers`, `favorites`, `skips`, `debates`, `flags`, `progress`, and `labruns` (written by an earlier Quorum that ran in the page, read by nothing now; the name stays because stored collections are not renamed). `progress` holds one document, `learner`: the learner's progression (the stages on, the course terms met at their stops, the negation step, the run towards the next offer of the stages, each exercise's run and right answers, each exercise's guided form where it was set, when the negation offer was last answered), which the page also keeps in localStorage and takes from the document when another device or tab changed it (`practice/progress.ts`). It has no `at`, so that at a device's first sign-in the account's copy wins over a progression made on the device before. Syllogisms keeps its answers in `answers` too, with `mode: "syllogism"` and a shape of its own (`SyllogismDoc` in `src/app/types.ts`: the syllogism as the domain names it, the reply that was right and the one given, the situation, the grade, the counter-example and how it was judged, and with Blitz the time the reply took, or `timeout: true` and `said: null` when the time ran out, and the tutor's explanation in `explain`); `isSyllogism` in `core/util.js` tells them apart, `answerList` leaves them out, the Review tab counts them on their own (`review/syllogism-stats.js`), and a skip keeps nothing. Find a pair keeps its answers in `answers`, with `mode: "find"` (`chosen` is the relation asked for, `key` the relation the pair has, `relOpen: true` while the tutor has not yet judged the learner's own pair); the Relations statistics, draws and recent list leave them out (`answerList` in `practice/universe.js`), and the Review tab counts them on their own. Categories keeps its answers in `answers` too, with `mode: "categories"` (`thing`, `level` (the reference example's, 1 for a practice item), `stage` (since the stages; optional), `rows` with the answer and what was said for each category, `s1`, `grade`, `ask`, and `narrow` with `s2` when step 2 was asked; `CategoriesDoc` in `types.ts`), left out of the Relations lists the same way. So does Find an instance, with `mode: "instance"` (`cats` and `labels` as asked, `possible`, `said`, the words written or `null` for "nothing is", `thing` when the data knew it, and `grade`, `pend` for a thing the data cannot check; `InstanceDoc` in `types.ts`). A pair set aside with Skip once it is named (before that Skip only asks for another relation) goes to `skips` with `from: "find"` and `asked` (the relation), under a key of its own, `f_<relation>_<hash of the pair>_<words>` (`findSkipKey` in `practice/skips.js`), so it never hides a pair of the Relations draw; Review > Skipped lists it, and it leaves the list when that pair is answered for that relation. Their document shapes are defined by `app.js`. Do not rename a collection or change a shape without a migration: answers already stored (in a published artifact's database or in a browser) depend on them.

## Data

The term data (the Dudra terms, their classification chains, the everyday-items list and aliases, as exported from the knowledge base) is kept in two places: the open data `src/data/drill-data.json` (about 135 KB, plain) is in the repository, and the definitions and notes are on the server and in the git-ignored folder `data-private/`. ## Voice

Voice is on trial. **Settings** has one row for it, a **Voice** switch marked Experimental: it is the kill switch, and with it off the page has no voice at all and `voice.js` does nothing. Its default is the build's: off in the real app, on in a Preview (staging, a pull request build), where `vite.config.js` defines `__PREVIEW__` from `iconSet()` (`scripts/lib/icon-set.mjs`) and the PWA platform passes it as `platform.preview`; `voiceOn` in `src/ui/speech.ts` lets the device's own choice (`rd-voice`, in the export file) win. The choices are in the **Practice options** of Relations and Pervasions, in a Voice section: a **Read aloud** switch, **Answer by voice** (Off, Tap the mic, Hands-free) with a chevron into the Voice page (the voice by accent with a sample, the speed, what each answer mode means, and how a heard answer is taken: wait for Confirm, or go on by itself). **Read aloud** says each question when it appears (the pair and the relation question, each cell's prompt in Relations, each statement in Pervasions); a speaker switch in the top bar, next to Blitz, pauses and resumes it for this visit (`state.voice.muted`, not kept). **Answer by voice** puts a microphone, an icon with no label, in the middle of the pair bar, to tap (or press V), or, in Hands-free, listens by itself after each question; it is lit while it listens. Under the answer controls the voice bar has something in it only while there is something to say: what is heard as it is said, a miss, the answer that waits, or, when the first question was held back, a button to hear it. Both use the browser's own speech: `speechSynthesis` for the voice and `SpeechRecognition` for hearing, so there is no service or key of the app's. Chrome's recognizer sends the audio to Google to turn it into text; the app records nothing and stores only the answer, in the same documents as a typed one.

A heard answer does not go on at once. It waits on the screen of the question it answers, as "Heard … taken as …" with **Confirm** and **Change** (Enter and Escape, or "yes" and "no" said aloud); saying another answer replaces it. "After an answer is heard" in the Voice page of the Practice options chooses between waiting for Confirm and **Go on by itself**: the answer shows a running bar (2 seconds in Blitz, 4 otherwise) and goes on when it ends, unless Change stops it. While an answer waits the Blitz countdown stands still and goes on from the same place at Confirm or Change, and the wait is not counted in the response time (`holdClock` and `releaseClock` in `debate/flow.js`).

| Part | What |
|---|---|
| `src/ui/speech.ts` | the two browser APIs: the English voices of the device (best first: Edge's natural voices, Apple's premium ones, Google's, then the rest; without the macOS voices that Chrome cannot load; each with its accent, which the Voice page groups them by), `voiceOn` (the default of the Voice switch), `speak` (like the recognizer, it is not trusted to say it has ended: a reading that the browser never ends is taken as ended after a time that follows the text), `listen` (up to five guesses of what was said, one restart when the first start opens no microphone; it does not trust the recognizer to say it has ended, because Chrome on Android sometimes never does after an interruption, so an error, an answer, a stop or 20 seconds each end it after a short grace) |
| `src/domain/spoken.ts` | reading the guesses as an answer: `spokenReply` (Accept or Why?, in any wording, with an example said in the same breath), `spokenRelation` (by name or number, or as the text written under the option, found with the pair's own terms: "all dogs are persons, but not the reverse"; three possibilities needs a direction), `spokenDirection` (which term is inside, as the phrase, "A in B" however the recognizer writes it, the term alone, or first and second), `spokenExample` (a practice item, also when misheard, or "nothing"), `spokenConfirm` ("yes" or "no") |
| `nearestItem` in `src/ai-shared/lookup.ts` | the practice item or alias nearest to misheard words ("a medal table" is a metal table) |
| `src/app/shell/voice.js` | what the screen asks and what to say for it, when to speak and listen, the answer that waits and its confirmation, and applying what was heard through the same calls as a tap or a typed answer (`sayQ`, `choose`, a cell's text); the voice bar, the microphone of the pair bar, the Read aloud switch of the top bar, the Voice row of Settings and the Voice section of the Practice options |

After each render the page compares the screen with the one it last spoke for (`asked()`); a new screen stops what the old one started and drops an answer that waited. The first question the app shows is held: nothing is read or listened to until the person asks for it (Hear the question under the answer controls, the R key, pausing and resuming Read aloud, or the microphone; or taps or presses a key anywhere before the next question), so the app never starts talking before people have looked around. "I don't know" (`spokenDontKnow`, checked before the words are read as an answer) takes no answer and gets a friendly nudge, said too when Read aloud is on. With Read aloud on, a question's Blitz countdown and its response time start when the reading ends. The settings are kept on the device (`rd-voice`, `rd-voice-*`).

`tests/unit/spoken.test.ts` checks the reading of answers; `tests/e2e/pwa/voice.spec.js` runs the flows with stand-ins for the two browser APIs, since the test browser has no speech service.

## Styling

`src/app/app.css` is an index: it imports the files in `src/app/styles/` (`00-tokens.css`, `01-base.css`, ...) and nothing else. Both builds import `app.css`, so a change to a stylesheet needs no change elsewhere. The tokens file carries the "Logic and Debate" design system values the page uses (booklet palette, felt per cover colour, rhombus marks).

The files are layers in cascade order, numbered to say so. The page grew by versions, and a later block overrides an earlier rule on purpose (`.grid` is set in `02-card.css` and adjusted in `15-result-chips.css` and `17-table-fit.css`, for instance). So the order of the imports is part of the style: add a new file at the end, or put a new rule next to the rules it belongs to, and move a rule to another file only together with what depends on its position. `tests/unit/styles.test.ts` checks that the index imports every file once, in order. The felt tiles sit next to `app.css`, so the url in the tokens file is `../felt-*.png`; Vite rewrites it for each build (a file in `dist/pwa/assets` for the PWA, a data URI in the artifact).

The Path's rules are `33-path-base.css` to `38-path-exercises.css` and `40-path-pages.css` (Review, the tutor's page, the flags, Settings and the options' pages), all under `.pa`; `39-path-bridge.css` styles the classic parts the Path hosts. A unit test keeps the Path's class names apart from classic rules that would reach them, both in its style sheets and in the classes its markup sets.

To check that a CSS change moved nothing, build before and after: `dist/pwa/assets/index-*.css` is minified, so an equivalent reordering of files gives the same bytes.

## Known gaps

- Quorum (several models and a judge answer an explain question) needs the app's server and only a Preview offers it; the artifact asks its host's one model. The tutor chat and Explain work in both, in the installed app through the server's tutor ([SERVER.md](SERVER.md)).
- "Check every answer with AI" (the practice options of an exercise, `rd-autoexplain`, on by default) asks for the explanation of a checked answer without a tap on Explain, in Relations, Pervasions, Find a pair and Syllogisms (`explainByItself` in `src/app/ai/tutor.js`, called by `afterCheck` in `src/app/ai/known.js`, which Relations, Pervasions and Find a pair run after a check, and by `finishSyllogism`). It asks only where the tutor can answer, once per answer, and leaves the screen and the focus where they are; the Explain button is still there when the question failed.
- Categories has one setting of its own in its practice options, how step 1 asks (`rd-cats-ask`: all at once, or one category at a time; carried by export and import); it applies at once to a thing not yet started and from the next thing otherwise. The stages it draws from are those switched on (`rd-stages`: the Stages section of the Progression page on the Path, the practice options on the classic page), shared with every exercise. Its answers count towards the offer of the stages that every exercise makes (`practice/stage-offer.ts`, rules in `stages.ts`): after a run of five right answers (both steps) on things new at the highest stage that is on the next stage is due, a right answer on a stage below counting for half (`LOWER_CREDIT`) (on the Path a stage that brings new terms comes with the first of them instead, and only a stage without them, or one the learner stayed on, waits for the run: see the stage station below), and after four wrong ones in a row taking it off is suggested; the count is never shown, and an answered or passed-over offer starts the run again (`rd-stage-run`, part of the progression). On the classic page only Categories shows the offer, and nothing is done without a tap. On the Path every exercise counts, the next stage comes in by itself (see the stage station below), and taking one off is an offer on the result as before.
- Find a pair has two settings of its own, both kept on the device and carried by export and import: the relation picked in the picker the diamond opens (`rd-findrel`, empty for Random, which draws) and "Suggest terms" in the settings of the exercise (`rd-findsuggest`, on by default), which gives the two pair fields a `<datalist>` of the course terms. The exercise has no timer, so there is no Blitz mode in which picking a relation would have to be closed.
- Find an instance has one setting of its own, in its practice options and carried by export and import: "Suggest things" (`rd-inst-suggest`, on by default), which gives the field a `<datalist>` of the practice items and, where the device has them, the reference examples it can check, those whose names hold the words typed so far. The categories it asks are those open at the stages switched on (`rd-stages`), from the next set; a thing named is graded whatever its stage.
- Syllogisms has two settings of its own, kept on the device and carried by export and import: the wording (`rd-syllogism-wording`, "take", the class's, or "formal") and the structure for a beginner (`rd-syllogism-guide`, on at first up to stage 4), which shows the structure for a beginner: under the sentence S is the subject, P the predicate and R the reason, and what each reply says in them. Its Blitz time is the third Blitz time (`rd-timer-syl`, "Syllogism time", 15 s at first), apart from the relation's and the example's, and the stopwatch is the one the other exercises use. What it draws from follows the stages (everyday things only up to stage 4). It has no notation: the options sheet shows these two settings, the Stages card, the Blitz card and, where the tutor can answer, the switch "Check every answer with AI".
