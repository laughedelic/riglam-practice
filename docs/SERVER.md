# The server

The app is static files plus one small Worker that answers `/api/*`. The Worker is what lets the installed app use the AI tutor without anyone's Claude account: it holds the model API key, checks who is asking, keeps each device and the whole app within a daily budget, and streams the answer back. Everything else the app does stays on the device, unless the person makes an optional account to keep their answers across devices (see "Accounts and sync" below).

Hosting is the same Cloudflare Worker that serves the static files (`wrangler.jsonc`, [DEPLOY.md](DEPLOY.md)). With `assets.run_worker_first: ["/api/*"]` only requests under `/api/` run the Worker; every other request is answered from `dist/pwa` without it.

## Layout

```
worker/index.ts         the Worker entry: createApp(...).fetch
worker/app.ts           routes, origin and proof checks, the budget, the server-sent stream (Hono)
worker/tutor.ts         one question: the model calls through the Anthropic SDK, the tool loop, the cost
worker/quorum.ts        Quorum, the tutor's mode of several models and a judge (Previews only): the run and its record
worker/speak.ts         reading aloud: the request's check and the call to Google's Text-to-Speech (the Chirp 3 HD voices)
worker/learned.ts       learned facts: what an explain answer says of each example the page could not check, kept per example and category
worker/budget.ts        the spend counters in D1: reserve, settle, the kill switch, pruning
worker/prices.ts        price per million tokens for each model; unknown models are charged at the highest rate
worker/config.ts        settings from variables, with defaults
worker/kit.ts           what the tutor knows, made from the term data: standing instructions, lookup tools, the notes
worker/bundled.ts       the open data file as the script carries it (only worker/index.ts imports it)
worker/course.ts        the course data as two rows of the course_data table
worker/magic.ts         the Magic Key from the secret, and the count of wrong proofs per caller and hour
worker/accounts.ts      optional accounts: the passkey ceremonies, sign-in state, deleting an account
worker/session.ts       session tokens and the cookie
worker/sync.ts          the server copy of a signed-in person's documents
worker/reports.ts       reports of learners' flags on the tutor's answers
worker/admin.ts         the maintainer's reading and deciding of those reports, with the admin key
worker/examples-admin.ts the maintainer's view of the learned facts, with the same key
worker/migrations/      D1 schema (applied with wrangler, see below)
src/ai/protocol.ts      the contract between page and server (shared by both): paths, headers, request, events, error codes
src/ai/proof.ts         the access proof (shared by both)
src/ai/magic-key.ts     reading the Magic Key from typed words or a link (shared by both)
src/account/            the device side: client, sync engine, outbox, passkey code (docs/ARCHITECTURE.md)
src/ai-shared/          the standing instructions, the lookup tools and the card, as pure functions of the term data (shared with the page)
src/account/protocol.ts the contract for accounts and sync (shared by both): paths, shapes, limits
src/report/protocol.ts  the contract for flag reports (shared by both): path, shapes, limits
src/pwa/speak.ts        the device side of reading aloud: the request and the errors the page tells apart
src/pwa/reports.ts      the device side of flag reports: the request, the removals kept for a later try
tests/worker/           Vitest tests with stand-ins for D1 and the model API
```

## Routes

| Route | What it does |
|---|---|
| `GET /api/health` | `{"ok":true,"tutor":"on"\|"off","accounts":"on"\|"off"}`, and `"quorum":"on"` or `"quorum":"optin"` where Quorum is offered (a Preview, see "Quorum"; the field is left out elsewhere), `"known":"on"` where the tutor is on and the server answers from its learned facts, and `"learns":"on"` where it keeps them (both: see "Learned facts"), and `"speak":"on"` where reading aloud can answer (see "Reading aloud"; independent of the tutor). `off` when the database, a secret or the kill switch says so. No sign-in. |
| `POST /api/speak` | One sentence read aloud. Body `{text, voice?}` (at most 700 characters, one of the voices of `SPEAK` in `src/ai/protocol.ts`; none is Charon), with the same proof headers as the tutor. The answer is the audio itself (`audio/mpeg`, no-store). Plain JSON errors otherwise: 400, 401, 403, 413, 429 (the day's characters are used up, with `scope` and `resetsAt` as for the tutor), 503 (off, or Google could not make it). See "Reading aloud". |
| `GET /api/course` | The definitions `{version, definitions}` to a request with a valid proof (headers `x-riglam-device`, `x-riglam-proof`); `?have=<version>` answers `{version, unchanged: true}` when current. 401 `not_granted` for a wrong proof, 429 `rate_limited` with `resetsAt` after 30 wrong proofs from one caller in an hour, 503 `unavailable` when the table is empty. |
| `GET /api/course/examples` | The device part of the reference examples `{version, examples}` ([DATA.md](DATA.md)), with the same headers and answers as `/api/course`; its version is the row's own. 503 `unavailable` while the server has no examples. |
| `POST /api/known` | What the learned facts answer of examples the page could not check, with no model call. Body `{cats: [two category ids], examples: [{cell, text}]}` (at most 8, each at most 200 characters), the same proof headers as the tutor; answers `{known: [{cell, text, line, by, half?}]}`, `line` in the tutor's form, `by` `learned` or `reviewed`, and `half` where only one side is known (see "Learned facts"). 401 for a wrong proof, 400 for a body of another form, 503 where `EXAMPLE_FACTS` is not `serve` or the table cannot be read. See "Learned facts". |
| `POST /api/tutor` | One tutor question. Body `{kind: "chat" \| "explain", cats: [category ids], turns: [{role, content}]}`, `quorum: true` to ask for Quorum, and on an explain question `examples: [{cell, text}]`, the learner's examples the page could not check, with `share: true` where the learner shares them (`src/ai/protocol.ts`, see "Learned facts"). The answer is `text/event-stream` of `delta` (a piece of text), `done` (`truncated` says the model ran out of room) and `error` (`code`, `message`); a Quorum answer also has `step`, `quorum` and `single` (see "Quorum"). Requests that cannot be served are plain JSON errors with a status: 400, 401, 403 (another site's `Origin`), 413, 429, 503. |

| `POST /api/account/key`, `GET /api/account/key` | An account carries the Magic Key (needs a session and the access proof), and gives it to its signed-in devices. See "Accounts and sync". |
| `/api/account/...`, `POST /api/sync` | Optional accounts and the server copy of the documents; see "Accounts and sync". |
| `GET /api/admin/flags`, `GET /api/admin/flags/:device/:id`, `POST /api/admin/flags/:device/:id/decide` | The maintainer reads the reports the review sent on and records a decision, with `Authorization: Bearer <RIGLAM_ADMIN_KEY>`. Off without that secret. See "Maintainer access". |
| `GET /api/admin/examples`, `POST /api/admin/examples/decide`, `POST /api/admin/examples/delete` | The maintainer reads the learned facts (the disputed ones first), settles a row with an answer, or removes an example's rows, with the same key. See "Maintainer access". |
| `POST /api/flags` | Reports of flags: `{send?: [{id, flag, answer}], withdraw?: [id], status?: [id]}` with the same proof headers as the tutor; answers `{stored, withdrawn, status?}`. See "Flag reports" and "Reviewing flags". |

The request carries only what the learner typed and the page's own state (the card of the pair and the conversation). The standing instructions, the lookup tools and the notes ("fine points") are on the server; the notes never reach a browser.

**The kit.** `worker/kit.ts` makes the tutor's knowledge per Worker instance: it reads the two rows of the `course_data` table (`worker/course.ts`), puts them together with `drill-data.json` (bundled into the script) as the knowledge base exports them ([DATA.md](DATA.md)), and builds the instructions and the two lookup tools from `src/ai-shared`, the code the page uses too. An instance looks at the table again after a minute, so `npm run data:publish` gives the tutor new data with no deploy. Without the rows the tutor is off. The row `examples`, where it is there, gives `classify_example` the reference examples to fall back on and adds the tool `examples_of` (the examples of a term, up to a level); without it, or when it is not JSON, the tutor has the practice list alone and no such tool.

**The definitions.** `GET /api/course` (`worker/app.ts`) returns the definitions to a request whose proof fits the Magic Key (`worker/magic.ts`), with the version they were loaded at; `?have=<version>` is answered with `{unchanged: true}` when the copy is current. Wrong proofs are counted per caller and hour (`guesses` table, 30 an hour). A guess is taken in one statement before the proof is looked at, so requests that arrive together are held to the limit too, and a proof that fits gives it back; past the limit the answer is 429 with `resetsAt` and `scope: "caller"`, and the proof is not even looked at. If the guess cannot be taken (the database fails, or the Worker has no database binding) the proof is not looked at either and the answer is 503 `unavailable`, so a failing or missing counter does not let anyone try keys without limit. A caller whose proofs always fit leaves no row in the table. The tutor route answers a blocked caller the same way, so the page tells a wait from a refused key. The notes are never sent. The rows are loaded with `npm run data:publish` ([DATA.md](DATA.md)); until they are, `/api/course` answers `unavailable` and the tutor is off. The same answer is given when the definitions row is not a JSON object (a row written some other way; the Worker looks at it once per version before sending the stored text as it is).

Error codes the page can see: `rate_limited` (the device's or everybody's budget for the day is used, or the model is busy), `not_granted` (the proof does not match), `prompt_too_large`, `bad_request`, `refused` (the model declined), `unavailable` (the tutor is off or failed). The details of a failure go to the log, never into the response.

## How the app uses it

The installed app (`src/pwa/tutor.ts`, the `tutor` capability of the platform, [ARCHITECTURE.md](ARCHITECTURE.md)) offers the tutor, Explain and the follow-up chat only when two things hold: this device has the Magic Key, and `GET /api/health` answers `tutor: "on"` within a few seconds. Otherwise the page hides them, as it does without a network. A question sends the card of the pair (without the instructions and the notes, which are the server's) and the conversation; the answer is shown as it arrives. A refusal reaches the person in plain words: the day's budget is used (it says whether it was this device's own or everybody's, and when the tutor is available again in the person's own time; the rest of the app keeps working), no connection, the conversation is too long, or (when the proof is refused) the tutor goes away until the next visit.

To try it locally, run the Worker and the app together with `npx wrangler dev` after `npm run build:pwa`: apply the migration to the local database (`npx wrangler d1 migrations apply riglam-practice --local`) and put `ANTHROPIC_API_KEY` and `RIGLAM_DATA_KEY` (any Magic Key) in a file named `.dev.vars` (git-ignored), and load the course data with `npm run data:publish -- --local`. `npm run dev` alone has no server, so the tutor is off there.

## Who may ask

The app is open to anyone with the link, but the tutor costs money, so a request must prove that its sender has the Magic Key (the words in the shared link, [DATA.md](DATA.md)). The page makes a random device id once and sends it with a proof: `HMAC-SHA256(key, "riglam/tutor-proof/1:" + device id)`, base64url (`src/ai/proof.ts`). The Worker holds the same key as a secret, recomputes the proof and compares in constant time. The key itself is never sent. A request with another `Origin` than the app's own is refused.

The device id is not a secret and proves nothing alone; anyone with the key can invent ids. The per-device limit therefore stops accidents and one heavy user. The global limit and the cap on the API account are the real limits.

## Budgets

Money is counted in micro-dollars (millionths of a dollar) per UTC day, in D1:

1. Before the model is called, the Worker holds back an assumed cost (`RESERVE_USD`) against the global counter and the device's counter, each in one conditional `UPDATE ... WHERE micro + hold <= cap`. Two questions that arrive together cannot both pass a budget that has room for one. If either has no room the answer is `429` with `retry-after` (the seconds to the next UTC midnight), and the error says whose budget it was (`scope`: `device` or `global`) and when it starts again (`resetsAt`, the next UTC midnight); nothing is held.
2. When the question ends (answered, cut off, refused, failed, or the page went away), the held amount is replaced by the real cost, from the token counts the API reports. A question that ends in an error is charged for what the model had used.
3. One line per question goes to `usage_log`: time, device id, kind, model, rounds, token counts, cost, outcome. No text of any question or answer is stored. The exceptions are the record of a Quorum run, where the server offers Quorum and the device turned it on (see "Quorum"), and the learned facts about examples, where the server is set to keep them, the learner has been told and the device has not turned "Sharing examples" off (see "Learned facts").

If the Worker is stopped between steps 1 and 2 the hold stays, so a lost settlement can only over-charge the budget, never under-charge it.

The hold is an average, not the worst case: a question with several tool rounds can cost more than `RESERVE_USD`, so questions that run at the same moment can together overshoot a budget by up to a few times the hold per question (for the defaults, a device sending many questions at once could pass its daily budget). The daily budgets are therefore soft counters. The hard limit is the spend limit on the Anthropic workspace (step 1 of "Setting up your own"); keep it set, and raise `RESERVE_USD` if you want the counters tighter.

Variables (`wrangler.jsonc`, `vars`; defaults in `worker/config.ts`; a value that is not a sensible number falls back to the default):

| Variable | Default | Meaning |
|---|---|---|
| `TUTOR_MODEL` | `claude-sonnet-5-5` | the model; a name not in `worker/prices.ts` is charged at the highest rate |
| `TUTOR_EFFORT` | `medium` | `low`, `medium`, `high`, `xhigh` or `max` |
| `TUTOR_MAX_TOKENS` | `6000` | output limit per model call |
| `TUTOR_MAX_ROUNDS` | `4` | model calls per question (tool rounds); on the last one tools are switched off so the model must answer |
| `DEVICE_DAILY_BUDGET_USD` | `1.00` | per device and UTC day |
| `GLOBAL_DAILY_BUDGET_USD` | `8` | all devices together |
| `RESERVE_USD` | `0.05` | the hold per question |
| `REVIEW_MODELS` | `claude-sonnet-5-5,claude-opus-5-5` | the models that review flags, one review each (at most three; the rule needs two that agree) |
| `REVIEW_DAILY_BUDGET_USD` | `1.00` | all reviews of flags together per UTC day; the tutor's budgets are separate |
| `REVIEW_RESERVE_USD` | `0.10` | the hold per flag until its reviews have finished |
| `REVIEW_MAX_TOKENS` | `2500` | output limit per review call |
| `REVIEW_BATCH` | `5` | flags one scheduled pass reviews |
| `EXAMPLE_FACTS` | none | `record` keeps the learned facts, `serve` also answers from them (see "Learned facts"); `record` in production, `serve` on Previews |
| `EXAMPLE_FACTS_MAX_ROWS` | `50000` | most rows of learned facts |

Prices are in `worker/prices.ts`, copied from Anthropic's pricing page; update them when the page changes or when a model is added.

## The model calls

`worker/tutor.ts` calls the Messages API through the official SDK (`@anthropic-ai/sdk`) with streaming. The model does its own thinking depth (adaptive; the `thinking` parameter is left out) at the configured effort. Automatic prompt caching (a top-level `cache_control`) makes a follow-up question re-read the earlier turns at the cache price. The Worker runs the lookup tools itself and sends the results back to the model; a failing tool is reported to the model as an error result, not to the page. Server-side fallbacks to another model are not enabled: when the model refuses or is unavailable the page gets an error and nothing is retried on a different model.

## Quorum

Quorum is a mode of the tutor for testing on a Preview. With it on, an explain question (the explanation of a checked answer) is answered by three models and, where they disagree, a judge; the learner gets one answer, and the whole run is kept so that the models can be compared.

- **Offered.** The Worker offers Quorum only when the variable `QUORUM` is `on` or `optin`. It is set to `on` in the `previews` block of `wrangler.jsonc` and to `optin` in the production settings; a server without the variable has no Quorum and `/api/health` leaves `quorum` out. The two values differ in the default of a device: with `on` (a Preview) a device has Quorum on until it turns it off in the practice options; with `optin` it has Quorum off, answered by the one model as ever, until it turns it on, because a run waits for three models and a judge and takes noticeably longer. A server that offers Quorum to the public (production) uses `optin`, with budgets sized for the learners who choose it (`1.00` a device and `4` in all per day, apart from the tutor's). Production applies migration `0008` before the first release that carries this setting. The page offers the practice-options switch "Several models explain" and the chip "Quorum" under a result only when the device has the Magic Key and health says `quorum: "on"` or `"optin"` (`src/pwa/tutor.ts`, the `quorum` capability of the platform); what the device chose is kept as `rd-quorum` and wins over the default. The artifact has no Quorum: it asks its host's one model.
- **Asked.** The page sends the explain question as for the tutor, with `quorum: true`, but only for an answer with an example it could not check itself (the Examples line says "not checked yet"): the tutor's lines on those examples are the check, and that is where the models can differ. When every cell has a verdict the tutor only explains what the page computed, so the one model answers as ever and no record is kept; the chip says so. Only an explain question can ask for Quorum; a chat question is answered by the one model as ever, and so is a question when Quorum's budget has no room (a `single` event says so, and the tutor's own budget pays).
- **The run.** `worker/quorum.ts` calls Haiku, Sonnet and Opus at the same time (`QUORUM.models` in `src/ai/protocol.ts`), each through the tutor's own code (`runTutor`): the same instructions, lookup tools, notes and card. A model's answer is the text of its last round: what it said before a lookup is left out. It then reads what each answer says of each example, from the fact lines of the explanation (`src/domain/quorum.ts`). Where at least two answers put an example in different cells, Opus (the judge, at high effort) is given the learner's question, the drafts in random order and the examples they differ about, and writes the answer the learner sees. Where they agree, the answer of the strongest model that answered is shown. Nothing is streamed while the models work: `step` events say how far the run is, then the shown text comes as one `delta`, then `quorum` (the record, for the chip) and `done`. If no model could answer, the event is `error`. A call that fails is left out of the run and named in the record.
- **The page.** The text the learner reads, and the verdicts the page takes from it, are that one answer. The chip shows each model's and the judge's cell for each example the learner wrote, next to the page's verdict, and the answers themselves; any value can be flagged. Where the models differ among themselves, or the ruling cannot stand beside the page's verdict on the learner's cell, the page also writes a flag for that example by itself (`part` and `auto` are `quorum`, `runId` the record's id, no note; the rule is `quorumDisputes` in `src/domain/quorum.ts`); Review lists it as "Quorum (automatic)". A later run on the same answer rewrites such a flag while it is new and leaves one that was reviewed or resolved.
- **The record.** Every run that had a usable answer is saved in the table `quorum_records` (migration `0008`): the day (not the device, so the text is not tied to a person), the first turn of the question (the card of the pair with what the learner wrote, at most 6 000 characters), every call's answer, which was shown, whether the judge ruled, how many examples were disputed, the cost and the outcome. **This is the one place where the server keeps the text of questions and answers** (the learned facts keep the learner's examples, see below): only where the server offers Quorum (a Preview, and production as an opt-in), and only for a device that has Quorum on; the practice options say so, and a device with Quorum off adds nothing. Rows are not pruned. Read them in the Cloudflare dashboard's D1 console, or with `npx wrangler d1 execute <database> --remote --command "SELECT ..."`. A failing save is logged and the learner's answer is not affected. Delete rows with `DELETE FROM quorum_records WHERE ...` when they are no longer needed.
- **Budgets.** Quorum has budgets of its own, apart from the tutor's, so that it cannot use the tutor's up: `QUORUM_DEVICE_DAILY_BUDGET_USD` (default `3`), `QUORUM_GLOBAL_DAILY_BUDGET_USD` (default `12`) and `QUORUM_RESERVE_USD` (default `0.40`, the hold for one run), counted in the same `budget` table under the scopes `quorum` and `quorum:dev:<id>` and settled like the tutor's (`worker/budget.ts`). One run is three or four model calls, each with the tutor's lookup rounds; it is logged as one line of `usage_log` with the model `quorum`. The defaults are high because Quorum is for gathering analyses of the models; the `previews` block of `wrangler.jsonc` sets the values a Preview uses.

## Learned facts

What an explain answer says of an example the page could not check can be kept, so that the same example need not be sent to the model again once the answers agree, and later checks of the same example are answered from it.

- **Set.** The variable `EXAMPLE_FACTS` is `record` (keep them) or `serve` (keep them and answer from them); anything else, or none, keeps nothing. It is set to `serve` in the `previews` block of `wrangler.jsonc` and to `record` in production, which keeps them and does not answer from them. Apply migrations `0009` and `0010` before a release that sets it (without them the write fails, is logged, and the answer is not affected). `EXAMPLE_FACTS_MAX_ROWS` (default `50000`) caps the table: past it new examples are not added, and rows already there are still updated.
- **Named.** With an explain question the page sends `examples`, the learner's examples whose verdict is "not checked" with the cell each stands in (at most 8, each at most 200 characters). Only the lines of the answer about those examples are read; lines about the page's own reference examples, and a chat question, are not. A server that keeps nothing ignores the field, and a page whose learner turned off "Sharing examples" (below) leaves it out. The server keeps what the answer says only when the request also has `share: true`, which a page sends only where health said `learns` and the learner has answered the one-time dialog (or used the switch) on this device: the first question that would name examples waits for that answer, and a page that was open before the dialog existed sends examples without it, so nothing of them is kept.
- **Read.** The answer's fact lines (`Both: "the example" | class: X | A yes: reason | B no: reason`, `src/domain/verdict.ts`) give for each example whether it is A and whether it is B (when the answer has more than one line for an example, the last one that is sure of something counts, as on the page, where the last line for a cell is the one the note shows). One row is kept per example and category (`example_facts`, migration `0009`), so a thing met in one pair answers that category in another pair too. The example is keyed by its words as the page's lookup compares them (`factKey`: lower case, American spelling, no article); one longer than 80 characters is not kept. Nothing is kept for a pair whose category ids the term data does not have, and a class that is not one of its terms is kept as none. A side whose answer goes against what the term data's steps say of the class the same line names (the class External form, yet "B no" for a form) is a slip in one of the two, so it counts as unsure, as it does on the page. Without the migration the write fails, is logged, and the answer is not affected.
- **Rules** (`src/domain/learned.ts`). One explain question is one analysis: the tutor's answer, or a Quorum run with its models and judge. A first analysis is `checked` when two or more models all gave the same yes or no, `disputed` when they differed and the judge gave no yes or no, and `candidate` otherwise (one model, a judge's ruling, or models that were partly unsure; a model whose answer leaves the example out counts as unsure when another one names it). A later analysis that agrees with a `candidate` makes it `checked`; one that gives the other answer, or is itself split, makes the row `disputed`, and only the maintainer settles a dispute. An "unsure" changes nothing but the counters. A `reviewed` row (the maintainer's) is never changed by a model. `FACTS_EPOCH` is the version of the prompts and the term data: a row of an older one starts again with the next analysis. Only `checked` rows of the current epoch and `reviewed` rows may ever be served (`servable`).
- **Answered.** After a check the page first settles what the course's reference examples on the device can (`src/domain/known.ts`, tagged "by the course examples"), then sends the examples still open to `POST /api/known`. An example is answered only when both its rows, one for each of the pair's two categories, may be served; the answer is the tutor's line for the cell it was asked about (`knownLine`), so the page reads it as it reads the tutor's, tags the cell "from an earlier check" and stores it as Claude's verdict. An example known on one side only is answered when that side already fails the cell: a "no" where the cell wants a yes, or the reverse. One failed part is enough to say the example does not fit, whatever the other side is, so the line (marked `half`) has "unsure" for the other side and the page fails the cell at once. Proving that an example fits needs both sides, so half a fact never says "fits". The page keeps such a cell in the explanation's list of examples, and the explanation's answer then fills the other side in. What is left goes to Explain as before, and the explanation then treats the settled examples as checked. The route makes no model call, so it has no money budget; it needs the Magic Key. A pair of the learner's own, and a pair of two names for one category, are not looked up.
- **Dialog and switch.** Where the server keeps examples, `/api/health` says `learns: "on"` and the page (given the Magic Key) tells the learner once, before the first explain question that would name examples goes out: a dialog in the middle of the page asks "Share your examples?", says in a few words why (other learners get answers sooner where the server answers from what it keeps; we all build knowledge together), that nothing else is done with them and nothing about who they are is kept (and asks to leave names out), and that it can be changed in Settings. It has to be answered: Escape and a tap outside do nothing, and no key answers for the learner. Ok (share them) and Don't share answer it, and the question then goes out with that answer, so the first check is kept too where it is Ok; `rd-share-told` remembers on this device that the learner was told (it stays out of the export, so a new device asks again). The page also shows a row in Settings (the menu), "Sharing examples", on by default, which counts as the answer too: it is set once and forgotten, so it is not among the practice options of an exercise. It says in plain words that the server keeps the words of the example, not who wrote it, the pair or the cell, to build a shared reference of examples with other learners, or, where the server also answers (`known`), so that the same example can be checked later without the AI (the learner's checks are then answered from what it learned, from their examples and from other people's). Where Quorum is offered it adds that Quorum keeps its own runs, whatever the switch says. Off, the page names no examples in an explain question (`rd-share`, kept with the other settings in the export); checks and answers from the server work as before. Examples already kept are not taken back by the switch: the maintainer deletes them ("Maintainer access").
- **Flags.** A learner's flag that names an example (the page adds it to the flag on a cell's note when a learned fact settled the cell, and the panel of a Quorum run has it on every value) disputes what the server learned of that example when its report is stored (`flagFacts`): a `candidate` or `checked` row of the pair's two categories, which the stored answer names, becomes `disputed` at once, so it is no longer answered and no later analysis promotes it, until the maintainer decides. A flag whose answer names no categories disputes every row of the example, which costs the next learner an analysis and cannot make the app say something wrong. A `disputed` row stays so and a `reviewed` one keeps the maintainer's answer; both count the flag (`flagged`, migration `0010`). A report counts once: an edit of its note, or the same flag sent again, does not count again, and taking the flag back does not undo the dispute. A program's automatic flag (Quorum's) does not dispute anything: the models' disagreement already did, by the rules above. The daily limits of the flag reports bound how many a device can raise.
- **Stored.** The example as last typed, the category, the answer, the class and the reason, the state, how many analyses agreed and disagreed, which models said what last time, how often and on which days it was seen. Not stored: the device or account, the pair, the cell, where the learner put the example, the rest of the answer. **This table holds text a learner typed**; an example can still hold personal words ("my cat Misha"). Read rows in the Cloudflare dashboard's D1 console, and delete one with `DELETE FROM example_facts WHERE thing = ...`.

## Reading aloud

The page reads each question aloud with the browser's own voice. Where the server has a Google key it can read with a natural voice instead: **Google Cloud Text-to-Speech, the Chirp 3 HD voices** (`worker/speak.ts`, `POST /api/speak`). The voices are Charon (the default), Kore, Achird and Sulafat (`SPEAK` in `src/ai/protocol.ts`; the server accepts only these, so a request cannot name another voice); the person chooses in the Voice page of the practice options, and the device's own voice stays one of the choices and is the fallback.

- **On.** `/api/health` says `speak: "on"` when the database, the secret `GOOGLE_TTS_API_KEY`, the Magic Key and the switch are all there. It does not depend on the tutor. Without the key the route answers 503, the field is left out and the page lists only the device's voices. The page offers the voices only to a device that has the Magic Key and health says so (`speak` capability of the platform, `src/pwa/speak.ts`); the artifact has none (no network to Google) and keeps the device's voice. Voice itself is still the experimental switch of Settings, off in the real app.
- **The call.** The server sends the text (white space collapsed, at most 700 characters) to `texttospeech.googleapis.com` as `en-US-Chirp3-HD-<Voice>` in MP3, with the key in the `x-goog-api-key` header, and returns the audio as it came. It waits at most 10 seconds. Nothing is stored: not the text, not the audio, and the log line of a request (`usage_log`) has the voice's name, the characters counted and the outcome, with no text. Google's own terms apply to the text it receives; the Voice page tells the learner that the words of each question are sent there.
- **The key.** Create it in the Google Cloud console and restrict it to the Text-to-Speech API (an API restriction is what limits what a leaked key can do). A server cannot be restricted by address on Workers. A key that is also restricted to HTTP referrers (for example `*.example.workers.dev`) works because the Worker sends the address it was asked at as `Referer`; that only keeps the key from being used in another site's pages, it does not stop a copy of the key used from a script. Set it as the secret `GOOGLE_TTS_API_KEY` (`wrangler secret put`, and for Previews the Preview base configuration, see DEPLOY.md). Turn on a budget alert on the Google billing account too: Google's budgets alert and do not stop spending by themselves.
- **Limits.** Google gives 1,000,000 characters a month free for these voices, and bills $30 per million after that. The server counts characters per UTC day, for one device and for everybody, in the `budget` table under the scopes `speak` and `speak:dev:<id>` at 30 micro-dollars a character (`SPEAK_MICRO_PER_CHAR`), held before Google is asked and given back when it fails, as the tutor's are (`worker/budget.ts`). `SPEAK_DEVICE_DAILY_CHARS` (default 10,000) and `SPEAK_GLOBAL_DAILY_CHARS` (default 30,000, about 900,000 a month); `wrangler.jsonc` splits the free month between production and the Previews, which share one Google project. A request past a limit is `rate_limited` with its `scope` and the time the day starts over, and the page reads with the device's voice until then. The same switch as for the tutor stops it at once: `INSERT OR REPLACE INTO settings (key, value) VALUES ('speak', 'off');`.
- **The page.** `src/ui/speech.ts` plays the clip in one audio element, started silently by the first tap so that a clip that arrives after the request may play on a phone, at the speed chosen (the pitch stays), and keeps the clips of the visit (40 of them) so that a question read twice is asked for once. When the clip cannot be made (no connection, 8 seconds with no answer, a refusal, audio that does not play) the device's voice reads the sentence instead, and the page does not ask the server again for a few minutes (until the day starts over, after `rate_limited`). The first question the app shows is not read, as before.

## Accounts and sync

Using the app needs no account, and everything it keeps stays on the device. A person who wants their answers, debates, favorites, skipped pairs and progression on more than one device can make an account, which keeps a copy of those documents on the server. Export and import (Settings, "Your data") remain the backup in every case.

**What an account is.** A random id, a name the person chose (the passkey manager shows it) and one or more passkeys: a public key each. There is no email address, no password and nothing else about the person. A passkey is made and used by the browser or the operating system (Face ID, a fingerprint, Windows Hello, a security key); the server only checks signatures. Passkeys that sync (iCloud Keychain, Google Password Manager, a password manager) work on the person's other devices; one that does not (a laptop's own) can be signed in with from a phone, and a second passkey can be added to an account.

A passkey belongs to the host name of the app (`riglam-practice.<account>.workers.dev`, or a custom domain). Moving the app to another host name leaves the passkeys behind: export on the old address and import on the new one.

**Signing in.** The ceremonies are WebAuthn, verified with `@simplewebauthn/server` (attestation `none`, discoverable credentials, user verification preferred but not required). Each ceremony starts with a challenge the server stores for five minutes and accepts once. Signing in gives the browser a random token in a cookie (`__Secure-riglam-session`, `HttpOnly; Secure; SameSite=Strict; Path=/api`); D1 keeps only its SHA-256, so a copy of the database cannot be used to sign in. A session lasts 60 days and is extended when it is used in its second half, in the browser's cookie too (the response of any account or sync request that extended it sets the cookie again). An account keeps at most 20 sessions: a sign-in first ends the account's sessions that are over and those beyond the newest 19, so repeated sign-ins do not pile up. The passkey's counter only goes up, also when two sign-ins finish in the other order. Signing out removes the session (an ended one too); if the database cannot do that the answer is `unavailable` and the cookie stays, so the person can try again. Requests that change anything must carry the app's own `Origin`.

**Sync.** `POST /api/sync` takes `{cursor, writes}` and answers `{cursor, changes, rejected, more}` (`src/account/protocol.ts`). The device sends the changes it made since last time, each as the document (or `null` for a deletion) and `t`, the time it made the change; the server answers with every document that changed on the server since `cursor`, in the order the changes were accepted. For one document the later `t` wins and a tie keeps the server's copy; the writes that lost come back in `rejected` with the server's copy, which the device takes. Deletions are rows without data, kept so that other devices learn of them. The server never merges inside a document and never reads what is in one beyond its size. Times more than five minutes ahead of the server's clock are cut back to that, so one wrong clock cannot make a copy nobody can beat. The cursor must be a safe whole number; one beyond the newest number the account has (a copy restored from a backup, say) makes the answer start from the beginning, so that nothing stays hidden from the device. An account deleted while a request is under way gets `signed_out`, not an empty answer.

**Limits.** Settings in `wrangler.jsonc` (`vars`; defaults in `worker/config.ts`):

| Variable | Default | Meaning |
|---|---|---|
| `SIGNUP` | `open` | who may make an account: `open`, `group` (only a caller with the access proof of the tutor, so only people who have the Magic Key) or `closed` (existing accounts still sign in); it is checked again when the sign-up is verified (the request carries the same proof headers), because a ceremony lasts minutes |
| `MAX_ACCOUNTS` | `300` | most accounts |
| `MAX_DOCS_PER_ACCOUNT` | `5000` | most documents one account holds (it also holds at most as many deletion marks again, twice this number of rows in all) |
| `DAILY_WRITES_PER_ACCOUNT` | `3000` | document changes one account may send per UTC day |
| `CEREMONIES_PER_DAY` | `2000` | sign-up, sign-in and add-a-passkey ceremonies that may be started per UTC day, all callers together (each writes a challenge row, and anyone can ask) |

A document is at most 256 KiB, a request at most 200 changes and 4 MiB (counted in bytes as the body arrives), and an answer at most 500 changes and 4 million characters of documents (the first change is always sent; `more` says there are further ones). The server's copies of the writes that lost are part of that text: the ones that do not fit are not sent in `rejected`; those the device has not received yet come with the changes anyway, and the others are given a new place in the sequence so that they come with them too. Deletion marks count as rows, and a mark older than 90 days (by the time of the change) is dropped when the account would otherwise be at its limit, so a device that was away longer than that may not learn of a deletion. A request with more changes than the account may send in a day is answered `too_large` (413) and the device sends half as many at a time. At most 500 ceremonies are open at once, and an account holds at most ten passkeys. The limits on accounts, passkeys, open ceremonies and the day's changes are decided inside the statement that stores the row, so requests arriving together cannot pass them; the limit on documents is checked before the changes are stored, so a burst can pass it by about one request's worth per request in flight, which the daily limit bounds. These caps keep a stranger from filling the database or using up D1's daily write allowance, which the tutor's budget counters share.

**On the device.** Settings shows an Account row when `/api/health` says accounts are on (or this device used one before, so that an offline start still queues changes). Signed out it offers "Create account" (a name for the passkey manager, then the browser's passkey dialog) and "Sign in" (the browser offers the passkeys it has for this app). Signed in it shows the name, the number of passkeys and where sync stands, with "Sync now", "Add a passkey", "Sign out" and "Delete account". Sign-out first sends what is waiting, and needs a connection because it ends the session on the server. Syncing runs on its own: a moment after a change, when the connection returns, when the page comes back into view and about once a minute while it is open. Settings (the `rd-*` keys in localStorage) are not synced; Export saves them. Every open tab notes its own writes and follows a sign-in, sign-out or switch made in another tab; a document the server sends is not stored over one the page wrote in the meantime, and a change whose note could not be stored is kept and noted again at the next round.

**Switches.** `INSERT OR REPLACE INTO settings (key, value) VALUES ('accounts', 'off');` stops sign-up, sign-in and sync at once (like the tutor's switch, in the D1 console); the app then behaves as if there were no accounts. `/api/health` shows `accounts: "off"` until the migration `0002_accounts.sql` has been applied.

**Carrying the Magic Key.** A signed-in device that has the Magic Key asks its account to carry it (`POST /api/account/key`, with the access proof; `users.has_key`, migration `0004_account_key.sql`). A device that signs in to an account that carries it, and has no key, takes the key from `GET /api/account/key` and starts again unlocked. The server answers that request with whatever key it holds now, so an account that carries the key keeps working after the key is changed, and a device whose key stopped fitting asks the account for the new one. An account that never showed the key is refused (`not_granted`).

**Deleting.** `DELETE /api/account` removes the account, its passkeys, sessions and documents in one batch, and the app offers it as "Delete account" in Settings. The copy on each device is not touched.

## Flag reports

A learner can flag something Claude wrote (the explanation, a note on a cell, an answer in the chat) with a note on what is wrong. Where the server takes reports, a flag is also sent to whoever maintains the app, together with the stored answer it was made on (the pair, the learner's examples with their verdicts, Claude's explanation), so that it can be read with the whole exercise. Only a device that has the Magic Key can flag, so a device without it gets the Magic Key page, as Explain does; being signed in does not matter, and a report only records whether the sender was.

- `POST /api/flags` takes up to 5 reports and 50 removals. The headers are the tutor's (`x-riglam-device`, `x-riglam-proof`); a wrong proof counts against the caller like a wrong key does and is answered `not_granted`; after 30 wrong proofs from one caller in an hour the proof is not looked at and the answer is 429 `quota` with `retry-after`, even to a right one. A flag whose `caseKey`, `thing`, `part`, `model`, `n`, `shown`, `asked`, `note` or `suggest` is not text, or whose `pair` is not an object, is refused as `bad_request`. A report is replaced by a later one with the same flag id; a device signed in to the account that sent a report can take it back, and an edit made on another device of the account replaces the first device's report.
- Limits per UTC day: 20 reports per device id, 60 per sender address (a short hash of it is kept, not the address), 1000 in all; 20 000 reports held. A report is at most 8 KB for the flag and 48 KB for the answer. An answer that is too large for that is left out and the flag is sent alone.
- **Automatic flags.** A program can write a flag too, such as the disagreement between the models that explained one example (`auto: "quorum"` in the flag document; the kinds are `AUTO_FLAGS` in `src/domain/flags.ts`). They are sent like the others but counted apart, so that they cannot use up the day's hand-made flags: 100 per device id, 200 per sender address and 2000 in all per UTC day, and they count in the 20 000 held. The page sends the two kinds in requests of their own, hand-made first, so a full allowance of one kind refuses nothing of the other (a request that mixes them is refused when either kind is full). A value of `auto` that is not listed makes the flag an ordinary one.
- A report is data from a device and is not trusted: the server stores it and reads nothing of it beyond its size, and whatever reads it later treats it as text, never as instructions.
- The page marks a flag as sent (`sentAt`) and shows "Sent to the maintainer" in Review (and then "Answered", "With the maintainer", "Fixed" or "Decided", with the reply as plain text under the flag, once the review has got that far; a reply can be flagged in turn, which sends a flag with `part: "reply"` that goes to the maintainer without a model review); a flag that could not be sent (offline, over a limit) is tried again at the next start and after the next flag. Removing a flag takes its report back, and the removal is kept on the device until the server has it.
- **Switch.** `INSERT OR REPLACE INTO settings (key, value) VALUES ('reports', 'off');` stops reports at once, and the page then keeps flags on the device. `/api/health` shows `reports: "off"` until the migration `0005_flag_reports.sql` has been applied.
- **Reading back.** `status: [ids]` (at most 50) is answered with `status: [{id, state, reply?, replyAt?}]` for those of the ids that this device sent or that an account it is signed in to sent: the state is `sent`, `answered`, `maintainer`, `fixed` or `decided`, and the reply is the text the sender reads under the flag. Nothing else of the review is sent back.
- **Privacy.** A report holds the flag, the answer, the app version, the random device id, the account id when the sender was signed in, and the hash of the address. No name or email. No route sends other people's reports back; the maintainer reads them in the database.

## Reviewing flags

A scheduled pass of the Worker (`worker/review.ts`, cron trigger `*/10 * * * *` in `wrangler.jsonc`) reviews the reports that wait. Cron triggers run on the deployed Worker only, not on preview URLs. With nothing waiting a pass reads one table and stops.

- **What a pass does.** It takes up to `REVIEW_BATCH` reports in state `sent`, oldest first, and for each asks every model in `REVIEW_MODELS` for a verdict. A reviewer gets the reviewer's instructions (`REVIEW_GUIDE`, `src/ai-shared/flag-review.ts`), the tutor's lookup tools, and one message: the tutor's card for the pair, the learner's answer, the tutor's explanation and the flag. It answers with one JSON object (`verdict`, `cause`, `reply`, `fix`, `confident`) that has to parse exactly (`parseReview`). The rule in `src/domain/flags.ts` (`decideFlag`) turns the verdicts into the outcome:
  - `reply`: both are sure that the learner is wrong, or that the tutor's text was wrong. The reply is shown to the sender (state `answered`); a tutor fault is kept as the cause `tutor` for the list of tutor improvements.
  - `fix`: both are sure that it is wording only. The reply is shown (`answered`) and the change waits to be made.
  - `escalate`: the fault is in the data, the rules that build pairs or the grading; or the reviewers disagree, are unsure, or fewer than two answered. State `maintainer`. When both are sure of the verdict and the cause, their agreed reply is shown meanwhile; otherwise there is none.
- **Without a model.** A follow-up on a reply (`part: "reply"`), a flag whose exercise was not kept, and one whose exercise cannot be read go to the maintainer at once. So does an automatic flag (`auto`, see "Flag reports"): it is stored in state `maintainer` with the outcome `escalate` and the reason "automatic flag (quorum): not reviewed by the models; the maintainer decides", so no pass ever takes it, whether the review is on or not. Models already compared the answers it is about, and what a reviewer would read is a program's summary, not a learner's words.
- **Budget.** Reviews have their own counter (`budget`, scope `review`) and their own daily cap (`REVIEW_DAILY_BUDGET_USD`); the tutor's budgets are not touched. A flag holds `REVIEW_RESERVE_USD` until its reviews finish and is then settled at the real cost; each reviewer's call is a line in `usage_log` with the kind `review` and the sender's device id. When the day's cap is used, the reports that need a model wait for the next day, and waiting does not use up one of a report's three tries. A pass that finds the cap used still looks down the list, up to 60 reports from the oldest, for those that need no model (a follow-up on a reply, an exercise that was not kept), which go to the maintainer as always.
- **Failures.** When the model API fails, the report is given back and tried by the next pass, up to three times; after that it goes to the maintainer with what there is (usually "fewer than two reviews"). A claim older than 15 minutes (a pass that was cut off) is taken over.
- **Edits.** The same words sent again keep their review, also when only the flag's own state or time changed. Changed words, or a changed answer, start the review again, and a review that is running on the old words is dropped. A report stored before the review existed has no digest of its words; it gets one from what the row holds when it is sent again.
- **What the reviewer sees from the device.** The stored answer is read into a fixed shape and every text is cut (`readReviewAnswer`); the learner's note, suggestion, question and what the tutor said are cut and written as quoted strings; the instructions tell the reviewer that all of it is material and never instructions. The reviewers can only read. The pair itself is still the one the device sent (its labels, notes and reference examples, cut but not checked against the data); the card's facts about the terms come from the server's own data.
- **Switch.** `INSERT OR REPLACE INTO settings (key, value) VALUES ('review', 'off');` stops the pass (reports are still taken); deleting the row turns it on. A `REVIEW_DAILY_BUDGET_USD` of `0` also closes it. The columns the pass writes (`reply`, `outcome`, `cause`, `reason`, `fix`, `reviews` and others) come with the migration `0006_flag_review.sql`; until it has been applied `/api/health` says `reports: "off"`.
- **Privacy.** The reviewing models get the flag, the stored answer and the course text that the card and the tools hold, through the same API as the tutor. The reply is shown only to a request that proves the Magic Key. `fix`, `cause`, `reason` and the reviewers' answers stay on the server for the maintainer.

## Maintainer access

`worker/admin.ts` is the door for whoever runs the app (a person with `curl`, or a scheduled task) to read the reports that the review sent on and to answer them. It does that and nothing else: no accounts, no documents, no budgets, no model calls.

- **Off by default.** It exists only when the secret `RIGLAM_ADMIN_KEY` is set to a random string of at least 32 characters (`npx wrangler secret put RIGLAM_ADMIN_KEY`); without it the routes answer 404 like any unknown address. The key is its own: the Magic Key does not open it.
- **The key.** `Authorization: Bearer <key>`. Wrong keys are counted per caller and hour in the same `guesses` table as the Magic Key's (10 an hour; then 429 until the hour is over, even for the right key). As for the Magic Key, a guess is taken in one statement before the key is looked at (requests that arrive together are held to the limit too), a key that fits gives it back, and when the guess cannot be taken the key is not looked at and the answer is 503 `unavailable`.
- `GET /api/admin/flags?state=maintainer&cause=&kind=&since=&limit=` lists reports (`state` is `sent`, `answered`, `maintainer`, `fixed`, `decided` or `all`; default `maintainer`; `kind` is `learner` for the flags people made or `auto` for a program's automatic ones, both when left out; at most 50, oldest first) with `counts` by state and by cause, and by kind within the state asked for. A report's `auto` is the name of the program that made it, or null. Each report has the flag (what it is on, what Claude said, the learner's note and suggestion), the pair, the outcome, cause, reason and `fix` of the review, both reviewers' answers, the reply the sender reads, whether the sender was signed in, and the `digest` of its words. A follow-up on a reply comes with the report it follows (`parent`). The device id appears only inside `ref`, the name a report is addressed by.
- `GET /api/admin/flags/:device/:id` is one report with the whole stored answer.
- **Automatic flags** reach the maintainer without a model reading them (state `maintainer`, outcome `escalate`, no cause, no reply, no reviews), and are decided on like any other; a reply is optional, and without one the device that sent it is shown only the state.
- `POST /api/admin/flags/:device/:id/decide` takes `{digest, state, reply?, decision?}`. `state` is `answered` (the automatic reply stands), `fixed` or `decided`. `reply` is what the sender reads next (plain text, cut to 1200 characters; without it the reply stays, with an empty one it is taken away); `decision` is the maintainer's own record (what was decided and where it was done), at most 1000 characters, never sent to a device. The `digest` is the one the report had when it was read: a report whose words were changed since is refused (409), so a decision cannot land on words it was not made on. A report that is `fixed` or `decided` is closed: a device stops asking about such a report once it has read that state, so a later change would never reach it, and a further decision on it is refused (409). The sender's own edit opens it again as a new report, with the earlier reply, decision and its time cleared.
- **Learned facts** (`worker/examples-admin.ts`, with the same key and the same counting of wrong ones; 503 where the table or its `flagged` column is not there). `GET /api/admin/examples?state=disputed&thing=&limit=` lists the rows of `example_facts` in a state (`candidate`, `checked`, `disputed`, `reviewed` or `all`; default `disputed`; at most 50, the most flagged first), with `counts` by state; `thing` keeps to one example, by its words. A row has the example as last typed, the category, the answer, class and reason, the state, the analyses that agreed and disagreed, the flags (`flagged`), who gave the answer last (`by`), whether it is of the current epoch, the days it was seen and the last analysis of each model. `POST /api/admin/examples/decide` takes `{thing, cat, answer, reason?}` as the list gives `thing` and `cat`: the row becomes `reviewed` with `answer` (`yes` or `no`) in the current epoch, which no analysis changes and the app answers from (`reason`, plain text cut to 200 characters, replaces the model's; without it the old one stays). `POST /api/admin/examples/delete` takes `{thing, cat?}` and removes that row, or all of the example's rows without `cat`: for personal words a learner typed. Both refuse a row that is not there (404). The text in a row is data, as in a report.
- **Everything is data.** The text in a report comes from a learner's device or from a model that read it, and every answer carries a notice saying so. Whatever reads it, a person or a model, treats it as text to judge, never as instructions, and decides nothing on its say-so.
- Migration `0007_flag_decisions.sql` adds the `decision` and `decided_at` columns; until it is applied `/api/health` says `reports: "off"`.

## Setting up your own

Nothing here is needed to build or test the app; without the database the tutor is simply off (`/api/health` says so).

1. Create a workspace, a spend limit and an API key in the Anthropic Console. A spend limit on the workspace is a cap that does not depend on this code.
2. Create the database and apply the schema, from a checkout, signed in with `npx wrangler login`:
   ```sh
   npx wrangler d1 create riglam-practice
   ```
   Put the `database_id` it prints into the `d1_databases` entry of `wrangler.jsonc` (binding `DB`, `migrations_dir` `worker/migrations`), then:
   ```sh
   npx wrangler d1 migrations apply riglam-practice --remote
   ```
   Apply it again after any pull request that adds a file to `worker/migrations/` (`0002_accounts.sql` adds the accounts, `0005_flag_reports.sql` the flag reports and `0006_flag_review.sql` their review and `0007_flag_decisions.sql` the maintainer's decisions on them, `0008_quorum_records.sql` the records of Quorum runs and `0009_example_facts.sql` the learned facts and `0010_example_flags.sql` the flags on them; the app works without them and `/api/health` says `accounts: "off"` or `reports: "off"`). Accounts need no secret and no extra service.
3. Store the secrets on the Worker; the first two are needed and the others are optional (the commands ask for the value at a prompt):
   ```sh
   npx wrangler secret put ANTHROPIC_API_KEY
   npx wrangler secret put RIGLAM_DATA_KEY     # the Magic Key: the words in the shared link
   npx wrangler secret put RIGLAM_ADMIN_KEY    # optional: opens "Maintainer access"; at least 32 random characters
   npx wrangler secret put GOOGLE_TTS_API_KEY  # optional: natural voices for reading aloud ("Reading aloud")
   ```
   Worker Previews do not inherit these secrets: give a Preview its own through the Preview base configuration (docs/DEPLOY.md).
4. Deploy as usual. Check `GET /api/health`.

**Kill switch.** In the Cloudflare dashboard (D1, the database, Console): `INSERT OR REPLACE INTO settings (key, value) VALUES ('tutor', 'off');` stops every tutor request at once; deleting the row (or any value but `off`) turns it on again. Archiving the API key in the Console or setting the workspace limit to zero also stops all spending.

**Privacy.** Without an account the Worker keeps spend counters and the usage log above, keyed by the random device id. With one it also keeps the account's random id, the name the person chose, a public key and the time of use per passkey, and the person's documents (answers they gave, debates, favorites, skipped pairs and the like), until they delete the account. Workers Logs are on for the lines the Worker writes itself (error names and statuses, never question text); per-request invocation logs are off.

## Tests

`tests/worker/` runs under plain Vitest (`npm run test:unit`) with stand-ins:

- D1 is a SQLite in memory (`node:sqlite`) with the real migrations applied, so the SQL that counts money is the SQL that runs in production.
- The model API is a `fetch` that answers with scripted server-sent events, so the real SDK client parses them (text, tool calls, `max_tokens`, refusals, HTTP errors, a call that hangs until the page goes away).
- The kit is made from a few invented terms in a fake database; the last test block runs on the real course data when `data-private/` is there (as in CI, [DATA.md](DATA.md)) and is skipped otherwise.
- Passkeys are made by a software authenticator (`tests/worker/authenticator.ts`) that produces the bytes a phone would (a `none` attestation with an ES256 key, signed assertions), so the library's real verification runs.

`admin.test.ts` covers the maintainer's door (off without the key, the counted key, what a list and a report show, a decision and the reply it gives, the refusal of a decision on changed words). `reports.test.ts` and `review.test.ts` cover the reports (the Magic Key, the limits, taking one back) and the scheduled review (which reports a pass takes, what each model is asked, every outcome, the budget, failures and retries, an edit made during a review, and what the sender can read back).

`accounts.test.ts` covers making an account, signing in, every refusal (another site's origin, a replayed or expired challenge, a passkey for another host name, a key that is not the account's), sessions, the limits, deleting and the switches; `sync.test.ts` covers who may sync, what a write may be, how two devices settle a document and the limits. They also cover the kit (the tools, the notes, a category id that is not the data's own, the wrong key, no text in the log), the proof, the settings, the prices, the counters (including simultaneous questions), every refusal path, a plain answer with the exact model request, tool rounds and their failure, the last-round rule, every failure of the model call, and the page going away.

What they cannot show is the Workers runtime itself. To try the Worker in `wrangler dev`, give it a local D1 binding (`wrangler d1 migrations apply <name> --local`), set `ANTHROPIC_BASE_URL` to a stand-in for the model API and use a throwaway Magic Key. Note that `wrangler dev`'s local proxy does not pass on a client that hangs up, so a page going away mid-answer can only be seen in the unit tests or on a deployed Worker (the `outcome` column of `usage_log` shows `aborted`).
